# Research — PRE-W3-COMPAT

**Phase 0, 2026-11-18.** The questions below concern implementation choices within the five Product Owner decisions in the [feature specification](spec.md). The three research threads covered admission, migration and drain/recovery. Findings describe source and platform behavior. Compatibility still needs a future executable and synthetic integration evidence.

## 2. Where can admission actually prevent effects?

**Decision.** Put admission at the receiving service, on every protected invocation, before any side effect. A trusted launcher binds a reviewed image digest to its service, credential mounts, permitted peers and private network for that generation. Guard the original Web request dispatch, the private API ASGI entry, and independently invocable job/cleanup commands. Keep the immutable predecessor payload in an unchanged image with separately versioned startup adapters. For example, a Node startup interceptor can guard dispatch on the existing socket and a Python ASGI launcher can wrap the existing app before serving it. Independently launched or unwrapped copies lack a path to active credentials, private upstreams, DB and delivery egress. Exercise that property on Compose. The final candidate can integrate the same decisions at its existing entry points.

**Rationale.** The Web ingress uses the socket peer for login throttling. The session helper updates last activity before ordinary forwarding. The API can durably register a nonce before its clinical transaction. The guard must run ahead of all three, including local auth, existing streams and direct private requests. Web checks its own database and calls API *liveness* today. The worker records bounded health in a heartbeat. None of these checks grants the next operation. [Web ingress](../../apps/web/ingress.mjs#L8) · [Session access](../../apps/web/auth/session.ts#L100) · [Signed forwarding](../../apps/web/auth/proxy.ts#L40) · [API boundary](../../apps/api/carepulse/identity/boundary.py#L136) · [Web health](../../apps/web/health.ts#L59) · [API health](../../apps/api/carepulse/health.py#L19) · [Worker status](../../apps/worker/status.py#L79)

**Alternatives considered.** A load-balancer switch misses private requests and autonomous work. Middleware in the later executable alone leaves the immutable process unguarded. A build header, caller-set GUC, static environment flag, role name or a green probe alone supplies no proof of the caller's effective eligibility. A new front proxy could change the source address used by the existing Web ingress.

## 3. How do we close admission and survive controller loss?

**Decision.** Put a small maintenance-owned control record in a private operations schema on the target PostgreSQL database, outside the published Alembic chain. Pin its target identity. Store the phase, owning epoch and admitted generation. Record unfinished multi-step work sufficiently to locate its durable outcome after a crash. Absence, unexpected shape or unreadability closes the gate. A scarce, nonpooled controller session takes a database-scoped session advisory lock over the whole cutover. Each new operation takes a **shared session permit** on a second key, checks the durable phase under a short shared row lock, and observes fresh head and effective authority. Close takes the conflicting row lock, commits closed admission, then takes the exclusive permit to wait out earlier invocations. Session permits span response/stream completion or delivery settlement, with no clinical transaction held open across network I/O. Fresh entrants during drain fail promptly. Only the owning controller can advance or reopen. Detailed ordering and recovery are specified in the [contract](contracts/cutover.md).

**Rationale.** A session lock can span multiple commits and disappears on connection loss. The persisted closed phase keeps a fresh process fenced after this loss. Holding ownership and running DDL on the same backend prevents a child migration from outliving its authority. Waiting for permits alone cannot prove that an external effect settled. The operator also needs the durable outcomes and actual stopped consumers. [PostgreSQL advisory locking](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS) · [Alembic connection injection in this repository](../../db/migrations/env.py#L9)

**Alternatives considered.** A process lock/file does not order independent participants against the database. A session lock without a durable phase reopens on crash. Heartbeat/TTL ownership can let a paused owner act after takeover. A long clinical transaction across SMTP cannot make acceptance transactional.

## 4. How do we prepare and advance the actual predecessor?

Compare original and target role definitions and memberships, schema/extension ownership, effective CONNECT/USAGE and routine ACLs. Expected new identities are the four constrained API/Web/worker/gate logins and the nonlogin identity owner with explicit migration SET membership. Verify `f01_private`, `f01_crypto` and pgcrypto's restricted digest/HMAC/random functions. Preserve the original auth, sender, operator and policy-seed limits. Prepare only a reviewed, explicitly missing delta under the existing administrative duty, with all product work fenced for the change. Reject incompatible existing objects, surprising ownership, extension placement, grants or historical data. Missing prerequisites in a preflight are a failed run with an unchanged application revision and data.

Advance with the existing supplied-connection path. Use one explicitly owned transaction per exact successor. Check the fenced owner, exact predecessor and intended successor in that transaction. Commit it before beginning another. Independently read back on a fresh connection, including after lost acknowledgement. Reuse published bodies in this order.

## 5. Which work can outlive the last transaction?

**Decision.** Track each affected invocation through its known outcome. Follow the actual one-shot sender under its narrow login, including polling, expiry, reclaim, cancel/material cleanup, transport and settlement. Preserve any ambiguous attempt and suspend retries under the closed gate. Compare database lease/generation/attempt evidence with the synthetic transport observation. Pending unattempted items may remain queued with known disposition.

**Rationale.** The general worker loops over health. The sender commits its claim, reads delivery material, calls Node/SMTP outside the database transaction, then conditionally commits the outcome. A timeout after provider acceptance can leave a retryable or terminal failure record. Lease expiry, an empty poll, a stopped PID or a recorded retry cannot resolve that ambiguity. [Heartbeat loop](../../apps/worker/main.py#L17) · [Claim through settlement](../../apps/api/carepulse/notifications/email_sender.py#L135) · [Claim and reclaim](../../apps/api/carepulse/notifications/evidence.py#L249) · [Sender runbook](../../ops/README.md) · [Lost acknowledgement control](../../tests/integration/test_delivery_sender.py#L245)

**Alternatives considered.** Killing every backend at closure can strand admitted work. Automatically retrying unknown SMTP acceptance risks duplicate delivery. Granting the heartbeat worker sender rights would expand its approved authority.

## 6. How can the controller verify security before reopening?

**Decision.** Compare catalog evidence against the reviewed per-revision baseline and exercise real-login metadata probes on the selected target. Include authenticated login and effective role, indirect membership/SET paths, LOGIN/BYPASSRLS, owners, PUBLIC, table/column/sequence/function/schema grants, required FORCE RLS policies, constraints, triggers, and F-01 proof/key-policy availability using bounded nonsecret checks. Verify both required access and forbidden effective access. Check stale pools and new connections. Validate product behavior on an isolated, equivalently configured disposable validation copy, keeping the cutover target closed to product work. Revalidate the live target before reopening, then exercise its authorized matched control. An effective-rights mismatch at a nominally correct revision denies the next operation.

**Rationale.** The reused auth and sender role names span generations. Legacy NOLOGIN constrains new connections only. Existing pools, already signed envelopes, the separate F-01 gate, actual scope enforcement and the credentials issued to each image all matter. Historical unknown approval or cleanup evidence cannot be supplied by a maintenance login. [F-01 scope](../../docs/f01-runtime-identity.md) · [PostgreSQL role attributes](https://www.postgresql.org/docs/17/role-attributes.html) · [PostgreSQL privilege inquiries](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-ACCESS)

**Alternatives considered.** Testing as the migrator hides denial behavior. Using only ACL strings misses effective privileges. Sending canary bookings to a closed target would violate the approved maintenance model.

All Phase 0 technical questions have design dispositions. Engineering demonstrations, independent review and operational approvals retain their own gates.
