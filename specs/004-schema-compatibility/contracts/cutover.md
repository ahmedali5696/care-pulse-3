# Compatibility admission and cutover contract

**Consumers.** The existing Web, private API, worker, one-shot sender and designated maintenance controller in the disposable synthetic environment. This is an internal service and operator contract. Browser routes, tenant permissions and domain payloads keep their existing meanings.

## Admission decision

Take the actual service/build identity and permitted peers from the trusted launch binding, the actual target and effective login from the connection, and the committed head, ownership epoch and phase from PostgreSQL. The only eligible combinations are below.

| Requesting set | Source open, single 0040 | Each of 0041, 0042, 0043, 0044, 0045 | Target open, single 0046 | Closed, draining, verifying, unknown or unverifiable |
| --- | --- | --- | --- | --- |
| Matched verified predecessor, valid original authority | Eligible | Fenced | Fenced | Fenced |
| Matched verified candidate, valid split authority | Fenced | Fenced | Eligible | Fenced |
| Mixed participants, unknown build/peer, wrong effective grants or retired credentials | Fenced | Fenced | Fenced | Fenced |

Eligibility permits the ordinary authorization check. It does not grant an operation. An inactive generation may remain present on its separate network with a live process. Both generations stay fenced while migrating. Closure overrides an otherwise matching head.

1. **Bind the caller and destination.** The launcher verifies actual image IDs against the reviewed manifest before mounting secrets or attaching private paths. Pin the generation's Web→API upstream and gate endpoint, isolate its transport/signing credentials and restrict the raw listeners. A crossed peer is denied before any Web session lookup, throttling, cookie or signing work. Private direct requests must pass the receiving API guard and normal signed boundary. Do not trust a version header, configurable role string, source address alone or caller-set session state. Preserve the original trusted TCP peer for Web throttling.
2. **Admit once at the real entry.** Acquire the shared work permit without waiting behind an exclusive drain, then in a fresh short transaction lock the control row for share and read it under READ COMMITTED. Validate the target binding, phase/epoch, singleton revision, manifest, actual login and expected effective rights, including forbidden rights. Check required dependencies over the scoped service connections. Register a durable pending reference where a multi-step effect could otherwise become unaccountable. Commit that short transaction before dispatch. Any verification error yields a denial. The controller's conflicting row update orders closure against this decision.
3. **Keep proof fresh on reuse.** At acquisition/reuse of a DB client, compare the physical target, authenticated and effective roles, expected head/ACL profile and current invocation. In a source wrapper this requires the original dispatch to own the pool work and a guarded client checkout at the original driver boundary. Include the separate Better Auth pool, API and gate pools, and independently launched work. Verify on the real backend before protected SQL and retain the existing transaction-local tenant/F-01 bindings. Returned pooled sessions carry no permit. Role/DDL/manifest changes during a managed cutover require the exclusive fence. Drift between requests invalidates the next admission. Predecessor client code and role privileges stay at the published baseline.
4. **Finish only the admitted work.** Hold the session permit across the response and any external delivery settlement. Recheck the gate at an independent downstream admission. If it has closed, the downstream call denies promptly and the earlier invocation must finish with an evidenced disposition. Do not queue a nested permit behind the drain or let a caller present a reusable continuation. An already claimed sender can settle its exact lease generation during drain with its original credentials. A later claim, retry or fresh business operation is a new admission. Close existing protected streams and account for their last emitted event.
5. **Deny safely.** Fenced HTTP protected routes return a sanitized unavailable response (503, no-store, no protected body, cookies or signed forwarding). API and Web liveness remain process-only. Readiness retains the existing 200/503 ready/not-ready interface and deadline, including Web's existing dependency checks. Worker live/ready retain private exit status and fresh-PID heartbeat semantics. A disabled poll/one-shot produces a sanitized unavailable result and no claim, send or cleanup. No marker, SQL, tenant or actor ID, raw exception, key, URI or credential reaches public diagnostics. Normal authentication, authorization and validation failures in an eligible generation retain their existing behavior.

The managed launcher is part of the executable under review. Test unwrapped and independently started services from their actual network/credential boundary. A writable manifest, alternate raw listener, unguarded pool, direct legacy DB route, bypassable sender command or delivery egress invalidates the evidence.

The admission reader checks the singleton head and expected effective ACL profile on the same target. Each actual service connection proves its own target, authenticated login and effective role with metadata inquiries within its existing rights. This split covers the auth, gate and sender logins without granting them direct access to the version table, private keys or clinical records. A role unable to complete its own required operation fails its service check. Do not use cached privileges to authorize a new request.

## Controller operations

The controller is an operator-only maintenance invocation. It accepts a trusted target reference, reviewed source/target manifest and requested action. Internal outcomes distinguish closed, draining, blocked on evidence, exactly one committed successor, and verified reopened. Do not expose an HTTP maintenance API or pass maintenance authority into a product container.

| Operation | Preconditions and atomic effect |
| --- | --- |
| Inspect / preflight | Read only. Confirm intended cluster/database, singleton source marker, exact reviewed chain and image digests, role prerequisites, effective ACLs/security, compatible data, fixture/preservation baseline, recovery basis and complete participant inventory. Reject earlier populated starts and unsupported heads. Failure leaves application data and revision intact. |
| Acquire / take over | Acquire the dedicated PostgreSQL session owner lock on a nonpooled connection to this target. A contender that fails to acquire may inspect only. After acquiring, claim a fresh epoch under row lock. For recovery, first ensure closed admission and independently verify the last committed state. An old session cannot reconnect and reuse an epoch. |
| Close / drain | With current epoch, commit `DRAINING` under the admission row lock before inspecting drain. Freeze new protected dispatch, polls, retries, sender invocations, cleanup and scheduled restarts. Wait on the exclusive work-permit lock. Check transaction outcomes, response/stream completion, pending references, claims, outstanding outbox and provider observations. Verify stopped affected consumers and absence of usable old product sessions, including idle/surviving pools. Keep the already-admitted work's authority until it settles. A missing or ambiguous outcome leaves the fence in place. |
| Prepare / advance | Under the fence, recheck source, source data, target binding, roles and the recovery evidence. If prerequisite provisioning was explicitly authorized, apply only its reviewed delta and repeat the read-only checks. Record phase `MIGRATING`. On the *owner-lock backend*, open one transaction, recheck epoch and measured predecessor, supply the connection to Alembic and advance exactly one named successor. Commit once. A fresh observer verifies that committed revision, expected security state and preservation sample before another successor. |
| Verify / reopen | While closed, check single target head, per-role effective authority, F-01 key and policy readiness, retained records, work dispositions and application/peer compatibility. Exercise the selected builds against an isolated equivalent validation copy for tests needing product effects. Check the actual target with nonbusiness probes using real logins. Reverify the target under the fence before the owner commits the single compare-and-set to open the matched generation. Hold traffic/consumer restarts until independent readback confirms the decision. All release paths still consult the current record. After reopening, confirm the supported service, job and receipt replay on that target. |

The controller keeps ownership across step commits, including a fault-injected migration. A transaction-scoped lock or a subprocess opening its own unguarded migration connection does not satisfy this contract. Admin-only operations such as role preparation/retirement must validate the current epoch and lock the same control row within the transaction changing the roles. An external stop can only restrict service. A late start or credential delivery cannot grant admission independently of the checked epoch and active generation.

Bind every start, takeover and reopen to the expected event, phase and epoch. A duplicate start after the winner advances returns the observed disposition. It cannot create a second event or convert itself into an authorized takeover. A designated recovering operator must claim the interrupted event explicitly and reconcile any pending admission references, including after loss of a guard connection.

### Delivery during drain

The sender can poll a whole organization or one known job. Before either dispatch, reserve a pending attempt in that scope so another poll cannot reclaim an outstanding attempt after lease expiry. A tenant-wide poll overlaps attempts for that tenant. If the claimed job is initially unknown, keep its wider reservation until correlation is established. Link the actual job and lease generation before transport. Run SMTP outside the clinical transaction. At the transport/finish boundary, distinguish confirmed acceptance, confirmed absence of a send, and an ambiguous acknowledgement. In the ambiguous case hold the attempt and its evidence before any retry, terminal material disposal or generic poll cleanup. On the immutable sender the separately versioned launcher must guard that boundary too. A fence that only checks the sender's eventual exit code is insufficient.

### Credential cutover

Block new legacy access and reacquisition through generation-isolated launch, network and secret delivery while draining. Allow settlement only for previously admitted work. Then disconnect/terminate settled old sessions, positively observe their disappearance, prevent auto-restarts, and test fresh as well as held-pool denial. Keep the irreversible retirement step after evidence of durable advancement where possible so the approved pre-first-commit recovery route remains available. Never re-enable credentials already retired. At target, verify legacy NOLOGIN and its lost clinical privileges, the distinct API, Web, worker and gate logins, nonlogin identity owner and least privilege of native auth, operator and sender. For role names shared across builds, isolate fresh credential issuance and invalidate previous sessions/material before enabling target access. Check private signing-key separation and issuance cutoffs under the existing policy.

### Recovery decisions

| Durable evidence after interruption | Permitted routine action within a separately authorized event |
| --- | --- |
| Verified 0040, no migration commit, intact data and still-valid source authority | Recheck work outcomes and all reopening conditions. The designated operator may retry or reopen only that matched predecessor. |
| Verified committed intermediate on this 0040-origin event | Acquire a new owner epoch if needed. Verify data, effective credentials and work outcomes, retain bindings and continue with the exact next published revision under the fence. |
| 0046 committed, initialization/retirement or verification incomplete | Keep closed. Independently check policy/key status, credential retirement, pools, preserved evidence, build pair and work outcomes. Resume only a verified pending step. Repeat at target has zero additional domain, policy/key, nonce or delivery effects. |
| Lost commit or reopen acknowledgement | Inspect the durable record and actual revision from a new connection. After an interrupted release, inhibit fresh work, account for any admissions that actually occurred, and revalidate. A lost client reply cannot authorize a second migration, a replacement key, another delivery or a second booking. |
| Wrong target, inconsistent state, uncertain transaction/SMTP outcome, unresolvable ownership or affected binding | Preserve evidence and keep both generations fenced. Exceptional restore, data repair, reconciliation of uncertain transaction or delivery outcomes, and actions risking data loss require **explicit joint Product Owner and Operations approval**. Reopening still requires every normal check. |

The migration operator, clinical Owner and F-01 gate have different duties. Maintenance/fixture setup cannot stand in for a product authorization, create Doctor provenance, enable historical-only writers at head or confer a T133 grant.
