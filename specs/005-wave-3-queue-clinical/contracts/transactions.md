# Wave 3 Transaction and Persistence Contracts

Proposed Phase 1 design, 2026-11-22. Sources: master §§2/8/11.4/12 and Domain §§4/6–11. Reuse [Wave 2 ordered transactions](../../003-wave-2-booking-scheduling/contracts/transactions.md), with current F-01 authority superseding historical shared-runtime assumptions. This document selects no migration implementation and claims no deadlock/runtime proof. [HTTP](http.md) defines strict operation families; [model](../data-model.md) defines evidence.

## Shared command boundary and lock order

1. Validate exact signed request and database-verified operation/resource. Bind the real service login/backend/xid, recheck live tenant/staff/session/security revision and relevant Manager capability under the existing authorization barrier. Resolve permitted resource IDs, never caller actor/role. Reauthorize receipt reads as well as mutations. F-01 activation may serialize same-clinic requests before inner domain locks; retain that boundary and demonstrate the actual blocker in tests.
2. Discover the complete existing Patient/source/target/cohort ID set through non-locking, tenant-checked reads. Lock applicable Patient lifecycle rows in ascending ID order, revalidate relationships and distinguish new-ID from lawful existing-ID archive handling. Discovery grants no authority or stable state.
3. Acquire applicable policy heads and Doctor/service-day schedule guards in established Wave 2 order: SCHEDULE → CAPACITY → FOLLOWUP → PRICE. For new QUEUE/ADMISSION policy consumers, use those heads after this existing order, QUEUE then ADMISSION, before control/lane locks; acquire only needed kinds. First QueueDay creation serializes with QUEUE-policy publication and snapshots the latest committed version effective for that date; pre-existing dated snapshots are never replaced. Multi-date work sorts dated guards/counters by date. Allocate each needed new/day-move number once through the existing counter before timed-capacity scans or Visit/source locks; a failed transaction rolls that allocation back. Preserve shared SCHEDULE attendance/close barrier: attendance takes compatible shared authority, final close exclusive; no late trigger acquisition after incompatible downstream locks.
4. Where needed, lock the one Doctor control before dated QueueDay/lane rows (stable date/lane order for multiple lanes). Count In Examination across **all dates/lanes**, not the selected view. For timed creation/move, fresh-scan counted intervals after allocation while holding policy/day authority; never opportunistically lock an unsorted Appointment in the scan.
5. Lock all existing source/target Appointments in ascending ID order before any Visit/source/claim; re-read status, day/lane, relationship, revisions and timed conflicts after waits. New target insertion is distinct from existing-row locking. For extension/move, existing target may sort before source and cannot be acquired late. If new required IDs appear after incompatible locks, reject/restart with fresh authorization rather than append an out-of-order lock.
6. Lock applicable Visit/source parent and claim/authorization/confirmation rows using the established upstream relative order. FOLLOWUP policy precedes source; existing Appointments precede Visit/source; source parent precedes a **fresh** source-event read/allocation, including an initially empty ledger. UNIQUE/MAX alone does not serialize first revision. Check original frozen authority, latest genuine Doctor restrictions, expected distinct revisions, confirmation scope/expiry and current eligibility after waiting.
7. Apply the owning state change and all required number/queue/history/attestation/claim/clinical or sensitive audit/outbox/receipt effects in one transaction. Deferred constraints inspect consistent final state; no network/file/delivery work under locks. Successful response follows commit.

This proposed extension must be checked against actual FK/trigger/function locks and existing policy writers before enablement; it is not a claim those locks have been proved compatible. Do not regrant an unchanged legacy writer that takes source before existing target or trusts caller-set GUC identity. If a composed path cannot honor this order, deny it and correct it in its authorized owner, preserving the upstream gate.

For prior-day admission, record explicit newly affirmed presence with actual actor/server time inside the admission transaction; never treat an old entry or separate stale attestation as sufficient. The overdue date boundary is strictly `service_date < current IANA Africa/Cairo date`; `requires_review` derives from it for Booked/Waiting, while In Examination is visible separately and not presumed absent. No extra Appointment state is added and an elapsed same-day Exact-Time slot never meets the date predicate. Completion value belongs to original service date, while source eligibility uses Cairo completion date; reporting remains B-26.

**Selected-day cutoff boundary (B-20):** Under current enabled B-07 cutoff policy and selected service date `D`, resolve the configured Cairo wall-clock time using IANA `Africa/Cairo`; choose `fold=1` for an ambiguous repeated time and the first valid local instant following a nonexistent time. Compare the resulting UTC instant against the authoritative database clock; before that instant, deny without business effects. The configured cutoff acts on `Booked` records for `D` regardless of the separate manual overdue date predicate. For each matched Appointment, serialize against check-in/cancel/No-show under the same appointment/claim and policy guards, recheck `Booked`, original date, presence, current enabled policy and eligibility after locks, and commit its terminal No-show, claim release, history, actual system/worker-origin audit, outbox and receipt as a single effect. CAS/receipt/result reconciliation makes a repeat, competing invocation or lost response incapable of adding a second release/audit/event/successful receipt for a previously changed Appointment. A failed transaction rolls back that Appointment's entire attempt; any records already committed remain terminal while remaining eligible `Booked` records can be scanned and processed on an authorized retry. No blanket one-shot `D` completion marker can suppress recovery after partial failure. B-25 owns durable invocation and retries, not B-20's business decision/transition; neither adds a new schedule/settings control.

## Follow-up authority consumed unchanged

Call B-10 qualification/source/extension primitives; do not create another authority or rewrite frozen evidence. Distinct actual-actor source decisions, NEW-date exceptions and confirmed extensions keep their upstream wire/storage/revision rules. Completed New Examination without explicit Doctor source decision can qualify under current policy; no fabricated Doctor DEFAULT. Receptionists cannot revise or bypass genuine Doctor OPTED_OUT/DEADLINE, including restrictions committed before a later action. A valid confirmed claim is not retroactively cancelled/repriced; later actions still obey current precedence.

Outside frozen deadline, B-18/B-19 require the distinct prior confirmed extension with reason and specific later/non-shortening date, protected source/policy/claim/authorization revisions and immutable actor evidence. A NEW-date exception cannot substitute. Cancellation/No-show releases; completion consumes once; release/rebook uses current policy/price with no inherited extension. Serialize these operations with genuine Doctor changes and upstream writers in both orders. Historical unknown provenance fails closed, never acquires invented clinical authorship.

## Receipts, failures and unknown outcomes

Use the existing TENANT receipt store with tenant + actual actor + operation + key uniqueness. New command digests include normalized operation/resource identifiers from path/query (Appointment/Visit/day/preview as applicable) plus canonical typed body; a body-only hash is insufficient. Preserve B-10's existing target-ID-plus-body digest and historical compatibility, rather than raw transport-byte hashing. Fresh signed/live authorization comes **before** initial lookup, post-wait lookup or conflict disclosure. Check requested-target authorization, current committed-resource visibility and the complete nested field allowlist; verify saved target relationships before success. Same-key/different visible authorized target is a command conflict, never success with another target's result; hidden/forbidden evidence denies without an oracle. Preserve original safe result/revision; never regenerate/reprice cached responses to repair unsafe historical evidence.

Bulk preview reuses immutable receipt projection/UUID, not a separate store. Existing cross-operation reads remain denied. The new preview-specific reader exposes only the exact same-actor/tenant preview referenced in signed bulk-commit scope, with its original operation and required revision set. Missing/foreign/unauthorized preview denies without exposing whether another actor's receipt exists. First commit rechecks live eligibility and revisions; original result_revision alone is insufficient. An authorized matching commit replay returns the original result without re-evaluating eligibility or emitting any events, after fresh actor/resource/field authorization. Matching preview retry returns the original preview UUID.

Same-key arbitration uses existing uniqueness; a losing aborted transaction rolls back all tentative effects, then a fresh signed/live-authorized transaction reconciles the committed winner. No continued SQL in an aborted transaction, blanket retry or arbitrary sleep. Security nonce/tombstone and minimal PHI-free denial evidence may remain separately durable; they are not successful business effects.

SQL/deadlock/lock-timeout, dependency or connection errors produce sanitized failure and pool-context cleanup. A failed command leaves zero successful domain/history/audit/outbox/receipt effects, including tentative number allocations. A lost commit acknowledgement/response is **unknown**, not proof of rollback: reconcile original key/result/current permitted resource before another mutation; do not mint a new key or blindly replay. If the actor's permissions were revoked after commit, live authorization still gates result lookup; a saved receipt cannot disclose formerly privileged data or renew former permission. Required unavailable policy/security authority fails closed.

## Migration, grants and executable proof

For each implemented command, align BFF/API method/path/purpose, DB route/body resource extraction and permitted stages, effective least-privilege tables/columns/functions, receipt recovery and audit/event scope. Preserve other-operation and same-tenant wrong-resource denials, not only cross-tenant RLS. Clinical scope is Doctor-only at both DTO and effective database boundary. Any unavoidable SECURITY DEFINER has fixed safe search_path, narrow EXECUTE and exact validated target; no implicit broad clinical projection or retired login fallback.

Future forward-only migrations start at the actual immediate predecessor and prove representative populated preservation, repeat/fresh behavior, atomic injected failure and correct revision/grants without changing published history. Maintenance-role setup and historical 0040 tests remain labeled substrate/predecessor evidence. New operation success requires actual API/gate credentials and real signed routing, with unchanged unrelated-scope denial tests.

Ordered races use transaction checkpoints plus observed PostgreSQL waiter/holder or lock-timeout witness. A started thread or sleep is not evidence of blocking. Record exact selected tests/commands, SHA/run, before/after committed rows/effects, cleanup and evidence limitations; then full ordinary Foundation at final executable SHA. Per [CI triage](../../../docs/postgresql-ci.md), identify failing test/step/run/SHA and establish application/test/environment cause before correction; after two speculative corrections, require new evidence. No retries/skips/relaxed assertions/timeout inflation to mask a failure. Protected T133 remains separately authorized.
