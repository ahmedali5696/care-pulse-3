# Wave 2 Transaction and Persistence Contracts

Sources: master plan §§2/7/11/12; Domain §§4/6–11; [spec.md](../spec.md) W2-FR-01/28/29. Aligned 2026-11-04: these are target design contracts, not amended implementation evidence; plan M1–M3 require independent engineering review. [HTTP](http.md) defines exposed Wave 2 operations; [data model](../data-model.md) defines stored relationships.

## 1. Shared security and commit boundary

Reuse the existing B-01 signed private request boundary and live-authorized SQLAlchemy transaction. Browser identity, tenant, role, net/number/rank and client `approved` flags are never authority. A valid signature alone is insufficient: recheck actual persisted session usability, tenant ACTIVE state, enabled/verified staff, role/security revision and operation permissions before a resource read, write or saved receipt is returned. Invalid foreign IDs are non-oracular 404; operator metadata credentials cannot reach clinical tables.

Use READ COMMITTED, transaction-local validated `app.organization_id`, FORCE RLS, composite tenant FKs and the installed non-owner runtime. Missing context fails closed. Keep the approved order, acquiring only applicable rows:

1. Organization/live permission barrier, including current staff/security revision and live operational_manager for settings; serialize grant/revoke and reauthorize before receipt recovery.
2. Patient lifecycle.
3. Clinic policy heads and service-day schedule serialization, including applicable number counter allocation.
4. Shared Doctor control when admission capacity is relevant.
5. Dated QueueDay/lane when applicable.
6. Existing target/source Appointment rows in stable ID order.
7. Source Visit/operational source revision and decision history, then claim/extension/confirmation rows in stable order; compare relevant Visit/source/policy/claim revisions.
8. Append history, sensitive/clinical audit, outbox and shared receipt; commit together.

Policy-head order remains P1: SCHEDULE → CAPACITY → FOLLOWUP → PRICE (applicable heads only), followed by dates/lanes and same-class IDs in stable order. Discover resource relations within tenant authorization, then lock/revalidate them in order rather than taking an out-of-order source lock. Separate operational source eligibility and genuine Doctor restriction provenance belong to the source/claim critical section shared by booking, eligibility changes, extension and later terminal consumers. Never acquire a lower-order patient/policy lock after a claim/source lock. No HTTP, SMTP, file/network operation or notification delivery while locks are held.

## 2. Receipt, retry and failure semantics

- Reuse D-09's one TENANT receipt store and B-01 canonical typed-body digest. Scope: tenant + actual staff actor + operation + `Idempotency-Key`. A transport nonce is separate: every HTTP retry is newly signed with a fresh nonce.
- After live authorization, identical validated request/key returns the original committed role-safe result; changed normalized content returns `409 IDEMPOTENCY_CONFLICT`. Do not reprice/revalidate a previously committed booking as a new creation or reapply today's archive guard to its receipt. Access revocation still denies the saved result.
- Concurrent same-key work resolves through existing uniqueness/receipt arbitration. A losing transaction must roll back tentative allocations/effects before reading a committed winner; never continue using an aborted PostgreSQL transaction. Different keys still obey counted patient/day, slot and source-claim guards.
- A domain success commits Appointment/snapshot/number assignment/history/claim where applicable, success audit, outbox intent and receipt together. A failed command leaves none of those successful effects. A rolled-back tentative number is not a successfully assigned number; every committed assignment is retained and never reused.
- Verified signed nonce consumption is separately durable under B-01 even if domain work fails; minimal PHI-free security denial evidence is not successful business evidence.
- SQL errors, timeouts/deadlocks, connection/dependency failure and aborts roll back/clean pool tenant context; sanitize outputs through existing stable errors. Do not promise automatic retry of every error.
- A lost commit acknowledgment/HTTP response means **unknown outcome**, not rollback. Reconcile the original authorized key/result/current resource with fresh authorization before another mutation; same-key retry may safely recover the result. Do not mint a new key or blindly replay non-idempotent work. Missing/unverifiable evidence remains unavailable/blocked, never false success.
- Every exposed Wave 2 mutation requires the shared key/receipt contract, not just booking. No finite key lifetime or receipt cleanup is authorized here; production retention/disposal stays with OPEN-OPS-03 / Issue #18. If the original key is lost, permitted current-resource reads may aid reconciliation, but a missing list result cannot prove rollback or authorize an automatic new-key retry. No new recovery route is introduced.

## 3. Pricing and calendar publication — B-06/B-07

For pricing/calendar settings, require Owner or live operational_manager within BR-036, including for preview and receipt recovery. Ordinary/revoked/disabled/foreign Receptionist denies. Bind audit/preview to actual actor, capability/security revision and changed scope. The shared permission barrier must serialize with Wave 1 grant/revoke so revocation-first denies, mutation-first commits its authorized evidence before revocation; no cached grant or stale saved preview may authorize later work (plan M1). No settings DTO writes staff, CAPACITY, Doctor Pause/case confirmations or clinical fields.

Lock current applicable policy heads in deterministic order and compare expected revisions. Append immutable D-04 versions rather than updating history; publish all changed heads and evidence atomically. Standard, Urgent, Follow-up and schedule inputs must be read as complete before-or-after versions. Urgent enablement requires a valid premium and configured operating periods; reject a standard-price edit that invalidates enabled Urgent unless expressly corrected/disabled. Later intake must independently revalidate its current schedule/premium eligibility; calendar changes never imply usable Urgent hours, automatic disablement or an extra activation prohibition beyond approved booking-conflict/validation rules. This does not introduce Urgent intake.

Per spec CHK011, validate finite percentage decimal values in [0,100] without an additional fractional-digit cap within existing request safeguards. Quote calculation, snapshot validation and persistence use the full accepted numeric value; never impose two-digit EGP scale on PERCENT or lose digits through fixed-context intermediate rounding. Round only final net once; retain the percentage exactly in immutable evidence. Both US2.7 examples must agree across quote/confirmation/readback. Invalid inputs or calculation/persistence failure leave no booking/number/snapshot/claim/history/success receipt/outbox effects; this adds no new lock, discount authority or production threshold.

Schedule preview is D-04/B-07, **not D-11**. A preview stores clinic/actor, candidate change, baseline schedule/policy and service-day revisions, affected confirmed IDs/revisions and explicit conflicts. It is advisory evidence, not permission to invalidate a booking.

At activation, reacquire the same publication barrier used by all bookings, read current schedule heads, recompute the complete affected set (including untimed `Booked`/`Waiting` on newly ineligible days) and the counted-status peak-occupancy conflict set, compare preview/relevant revisions and deny stale/unresolved changes. Cover recurring/calendar-wide changes and dates that had no service-day row at preview: locking only already-existing dated rows cannot prevent a newly booked date from escaping the check. Use the existing clinic schedule head as the common publication barrier, then deterministically lock affected day rows. New day rows must be acquired/created under that barrier. This reuses D-04, not a new global-lock service.

Activation neither cancels, reschedules, reprices nor changes status. Until the authorized later resolution workflow exists, a conflicting change remains blocked. Explicit cutoff settings affect validation/preview, but saving them invokes no No-show transition, scheduler or inferred closing time. Preserve future-effective queue policy versions; no queue setting command is added to Wave 2.

The affected-change set includes booking mode, manual slots, generated duration and timed overlap/effective limit. Preserve existing intervals and Open null times; candidate membership is a **new-booking** check, not a retroactive reason to rewrite confirmed intervals. Per the approved 2026-10-28 Product Owner interpretation, proposed date/work-period/break invalidation blocks future `Booked` and `Waiting`, including dates containing only `Waiting`; those changes do not retroactively disqualify `In Examination` or `Completed` care. Independently count timed occupancy from `Booked`, `Waiting`, `In Examination` and `Completed` on all relevant future dates, even if no `Booked` exists and overlap/capacity settings are unchanged; a proposed effective limit below existing peak blocks activation, including disabling overlap with overlapping bookings. Preserve their original dates, statuses and intervals. Effective limit is 1 with overlap OFF or current saved examination capacity with overlap ON; schedule publication never writes CAPACITY or a separate booking limit. A mode change affects new bookings clinic-wide, not historical mode. Cutoff-only changes show which still-Booked records become subject to prospective reconciliation, not an immediate state/interval invalidation. A review effect is not itself a cancellation requirement.

## 4. Exact-Time — B-08

`GET /slots` is a read-only advisory view with current schedule/day revisions. Resolve date overrides before weekly periods; holiday/non-working ordinary booking requires its toggle, and timed opening additionally requires an explicit positive date-applicable period. Open never enters interval capacity calculations or acquires a fictitious time cap.

Per spec CHK008, independently resolve the effective manual set: an explicit date-specific set replaces the weekly set for that weekday/date; absence inherits weekly, never merges. Validate the selected manual candidates against the applicable date/work/break/holiday rules. This selection does not change generated-grid anchors or supply hours. Preview recurring/date-specific manual changes under the same publication barrier and re-resolve the effective set at booking commit; existing intervals are not rewritten.

Validate manual/generated intervals against periods/breaks and Cairo gap/fold rules before offering them. Per spec CHK007, anchor each generated grid at its applicable working period's start and advance in positive duration-sized steps. Retain only full intervals ending within the period, omit break intersections without resetting the grid and discard trailing remainders. Then remove every generated interval intersecting a valid manual candidate. At confirmation, under the shared schedule/date barrier, recompute this same grid/eligibility and rescan currently counted timed Appointments for that Doctor/service date; do not trust a previewed slot ID alone. Retain terminal interval history but exclude Cancelled/No-show from reserving capacity; Completed remains counted for its service-day interval.

Per the spec's Product Owner clarifications, new timed endpoints must exactly match a current valid manual or unsuppressed generated candidate; arbitrary intervals are denied. New Open/timed bookings use the active clinic-wide mode. At confirmation reject past Cairo dates and starts already passed today, with no additional minimum lead duration. CHK002 imposes no maximum future horizon in requested-date availability or confirmation; evaluate current date/period/slot/capacity guards without an arbitrary cutoff or pre-generating all future candidates. Preferential Follow-up deadlines remain independently binding. Preserve prior commitments and receipt recovery independently of these new-creation checks.

Compare canonical UTC `[start,end)` instants. With overlap OFF, any true intersection denies. Per spec CHK006, enabling overlap requires configured Exact-Time slots and explicit live authorized settings-actor confirmation of current saved examination-capacity integer >=2 and its revision. Under deterministic policy-head locks, compare that evidence at staging/activation and read/recheck current CAPACITY at booking; never write it through schedule operations. With overlap ON, combine current reservations and candidate in an endpoint sweep, processing ends before starts at equal instants; peak simultaneous occupancy must not exceed current saved examination capacity directly, with no separate booking limit or additional ceiling. Counting all records that intersect a long candidate is incorrect when those records do not overlap each other. Preserve existing bookings; B-14 capacity controls remain later scope. Sharing the saved limit does not replace later shared active-examination counts or per-case Doctor confirmation rules.

## 5. Routine booking — B-09

After genuine authorization and receipt resolution, lock/recheck selected patient lifecycle using the existing new-Appointment guard. Lock current pricing/calendar/day state, validate date and optional interval, derive Doctor/MAIN/ROUTINE/New Examination/Booked server-side, calculate frozen EGP and enforce counted uniqueness. Persist through the shared Appointment/number/history/evidence components in the caller's one transaction; refactor the fixture-oriented D-05 persistence entry only as necessary without exposing its arbitrary-status input publicly.

Compare expected applicable PRICE/FOLLOWUP/SCHEDULE/source revisions, CAPACITY revision for enabled timed overlap and reviewed quote to the locked state, current saved capacity and recalculated amount. Stale new work returns 409 with no successful effects; never silently confirm at current-but-different pricing/capacity. Both roles can read the minimal pricing/quote projection and applicable capacity revision through slots; client expected base/net are equality checks, not authoritative snapshot values. Original committed receipt recovery remains prior to new-work validation.

Persist **no Visit, attendance or active QueueEntry**. Doctor Pause and disabled Routine walk-in do not deny ordinary booking or authorize an immediate-attendance convenience command. No minimum advance duration is invented. Patient/day uniqueness spans all classes/lanes and Booked/Waiting/In Examination/Completed; only Cancelled/No-show allow another counted new ID. Archive-first denies new creation; booking-first survives later archive with history intact.

## 6. Preferential booking/eligibility/extension — D-08/B-10

Use B-09's single booking transaction, not a second engine. After fresh authorization and receipt resolution, lock patient → P1 policy heads → service-day number counter → stable source/target Appointment IDs → source Visit/operational source state → claim/extension rows. Source locks exist even with no decision/claim row. Resolve visible same-tenant/patient/Doctor Completed Routine/Emergency/Urgent New Examination and actual completion provenance; Follow-up and exceptional-cancelled sources cannot qualify. Explicit hidden/missing IDs deny 404 before revision disclosure. Referenced source requires expected_source_revision, a separate operational token rather than clinical_revision; compare under locks **before both preferential and acknowledged fallback**. Source commands also compare Visit revision, extensions compare exact claim/Appointment and policy revisions. Exact token/old caller migration is M3 review, not assumed implemented.

**Source decision transaction:** all active authorized staff can record DEFAULT/OPTED_OUT/DEADLINE; non-DEFAULT requires nonblank reason, DEADLINE finite concrete Cairo date ≥ completion. No decision/DEFAULT uses current versioned clinic policy without fabricated Doctor authorship (initially seven inclusive local days). Persist actual actor ID/role/tenant/source/time and immutable actual before/after when revising, advance source revision and append sensitive audit/receipt atomically. Receptionists may revise Receptionist-authored decisions but cannot modify/replace genuine Doctor OPTED_OUT/DEADLINE. Preserve Doctor provenance beyond a latest-decision pointer; only genuinely authenticated Doctor revision changes it. Operational Receptionist evidence never writes Doctor clinical fields or a Doctor ClinicalRevision. General clinical correction stays B-16.

**NEW-date exception transaction:** a separate exact selected NEW-booking date may be authorized by Doctor with required reason or independently by Receptionist with optional reason; mandatory immutable audit for either. Confirm current source/policy revisions and Doctor precedence, Cairo lower bound and all ordinary date/start/slot/capacity/archive/patient-day/single-use guards. Freeze policy-derived or actual-decision source evidence, exact-date actor/role/reason/audit, approved date/deadline and EGP with Appointment/claim/history/outbox/receipt. No separately reusable approval or pending workflow. Missing Doctor decision is eligible under policy, not fallback. Effective OPTED_OUT denies preferential qualification; genuine Doctor DEADLINE replaces clinic default and no Receptionist exception exceeds it.

**Confirmed-extension transaction:** a separate operation for all authorized staff on the exact existing ACTIVE claim. Require mandatory reason and specific later/non-shortening Cairo date ≥ completion and ≥ latest effective confirmed authorization, with locked source/Visit/policy/claim/Appointment revisions. Append actual actor/role/tenant/source/claim/time, prior/new authorization and immutable audit; advance claim authorization revision under the same claim lock. No modification to original source/policy/price snapshot, no automatic move, no clinical revision forged for Receptionist. Released/consumed/absent/stale targets deny; no extension authorizes another claim. Later B-18 rechecks extension chain, Doctor precedence, current date/slot/day guards and revision before a move; price stays frozen and no authorization is inherited after release/rebooking.

**Every Receptionist path checks Doctor precedence at commit:** source decisions, NEW-date exceptions and confirmed extensions lock/revalidate genuine Doctor OPTED_OUT/DEADLINE, including restrictions added after confirmation. Doctor opt-out forbids a new Receptionist action; Doctor deadline cannot be modified or exceeded. A reason or Manager grant cannot override this. Do not retroactively cancel/reprice an existing confirmed claim when later source/policy changes; immutable original entitlement remains, while later Receptionist actions must obey current restrictions. Only authenticated Doctor restriction revision changes that source authority, with immutable provenance and expected revisions. Policy/source/claim/Visit locks must cover this check through commit, not merely at preview/read.

An ACTIVE source conflicts without fallback. Nonqualifying/consumed care can become New Examination only with explicit actual-type/ordinary-base/net acknowledgment and explicit discount reaffirmation under current revisions and all normal guards. No selected source means acknowledged ordinary fallback without automatic source selection. Existing committed receipt recovery reauthorizes first and returns original permitted result; new work with stale policy/source/reviewed price denies without partial number, claim, evidence or success receipt.

**Completion foundations (D-07/D-08, command later B-16):** explicit positive examination_occurred evidence binds actual actor ID/role, tenant, Appointment, Visit and server timestamp. Missing/false assertion cannot produce Completed/consumption. Serialize Appointment/Visit, source/claim and cancellation/duplicate completion in the common order; status/history, retained Visit, immutable attestation/audit/outbox and CONSUMED commit together. No Doctor note/signature/eligibility decision or ClinicalRevision is fabricated. D-07 proves its own support independently; D-08 adds claim consumption proof, not a reverse dependency.

**Forward-only review (#24/#25):** 0021/0022 are published and immutable. Plan M2 reviews separate operational evidence, source revision, legacy Doctor restriction mapping and completion attestation without rewriting clinical history/frozen claims. Incompatible migration or unverifiable new qualification fails closed, never synthetic backfill. New migrations require populated actual-predecessor/failure/RLS/grant and exact-SHA CI evidence; historical passing tasks/CI are not amended acceptance.

### Required race outcomes

These make spec Edge Cases explicit; later operational commands remain out of scope. Verify both lock orders where different outcomes are possible.

| Pair / authority | Required serialized outcome |
| --- | --- |
| Archive / new booking (CON-35) | Archive first denies new ID; booking first preserves the committed booking through later archive. Neither outcome leaves partial evidence. |
| Same patient/day bookings (CON-01) | At most one counted new ID; loser conflicts without allocation/snapshot/claim/history/outbox. |
| Different patients' numbers (CON-33) | Successful bookings get distinct clinic/day numbers; rolled-back tentative allocation is not a successful assignment. No gapless guarantee is added. |
| Price/schedule/source edit / new confirmation (INV-26; master Wave 2 exit) | Confirmation first freezes its reviewed valid values; edit first makes stale expected revisions/quote fail 409. An identical committed receipt still recovers the original result. |
| Activation / first booking on a date absent at preview (CON-27) | Booking first changes the freshly recomputed affected set/day revisions and prevents stale conflicting activation. Activation first publishes one policy; stale booking rejects, refreshed booking must obey it. Both cannot commit contradictory eligibility. |
| Two timed confirmations (CON-24) | Rescan after serialization; default intersection denies or enabled peak stays within capacity. No preview reserves a slot. |
| Source decision or target-scoped extension / claim (D-08/B-10; CON-10/16) | After day-counter-before-source locking, decision first advances operational source_revision and makes submitted expected_source_revision fail with 409 for both preferential and acknowledged fallback confirmation; confirmation first freezes its reviewed result and later source edits cannot revoke it. An extension requires the exact existing confirmed claim/revisions; an absent/stale/released/consumed target cannot authorize a new claim. An extension grants no entitlement to a competing booking. |
| Manager settings / Owner grant-revoke (#25; INV-20/26) | Permission barrier first: revocation-first denies settings, preview activation and receipt recovery; mutation-first commits authorized actual-actor evidence before revocation. Disabled/suspended/stale-grant actors never use saved authorization; no Owner-only account/capacity or Doctor control escalation. |
| Doctor restriction / Receptionist decision, NEW-date exception or confirmed extension (#24/#25; CON-10/16) | Restriction-first denies modifying/bypassing Doctor opt-out/deadline or conflicts stale revisions. Receptionist-first may commit only while allowed, preserving frozen evidence; later restriction constrains future actions, not prior confirmation. Only Doctor restriction revision can change that authority. Test each of the three paths, not only booking. |
| Receptionist source revision / another decision or fallback (#24; INV-10) | One expected source revision wins; loser conflicts with no before/after/audit/receipt mutation. Decision history preserves actual actor and genuine Doctor provenance; no clinical_revision substitution. |
| Two confirmed extensions / release or B-18 move (CON-16/22) | Claim authorization revision serializes: no shorter second extension, stale/released/consumed target cannot append, release inherits none. B-18 later rechecks the latest chain and current Doctor restriction under locks; no snapshot/price rewrite. |
| Positive completion / cancellation, duplicate or source claim (AC-05/06; INV-05/10/23) | Correct state and positive attestation/history/consumption commit once; missing/false/stale evidence and losing cancellation/duplicate leave no partial terminal or claim effect. A new source claim sees committed completion evidence only; no fabricated Doctor author. Persistence simulation now, actual B-16 command later. |
| Claim / terminal release or consumption (CON-10/11/22) | Before release, busy source conflicts. Release first permits fresh qualification at current price. Consumption is atomic/permanent; another request can only take the acknowledged ordinary fallback under all guards. Failed terminal write leaves the old claim active. |

Approval expiry equality is unusable (`now >= expires_at`); no production duration is chosen. The confirmation race remains a D-06 persistence simulation, not a shipped admission command.
