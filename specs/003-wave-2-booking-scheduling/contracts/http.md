# Wave 2 HTTP Contracts

Phase 1 interface design for **B-06–B-10 only**, not an assertion that routes exist. Master plan §§2/7/11.1 and the approved role/field matrix govern. Reuse [Wave 1 common protocol](../../002-wave-1-security-core/contracts/http-and-operator.md#common-protocol) and [security lifecycle](../../002-wave-1-security-core/contracts/security-lifecycle.md); [transactions](transactions.md) defines atomic effects and [data model](../data-model.md) defines persistence.

## 1. Shared protocol and authorization

- Browser routes below use `/api`; private FastAPI equivalents replace that prefix with `/v1`. Retain any existing internal BFF forwarding path as an implementation detail. No host-published API, direct browser privilege path or session cookie/bearer forwarded to FastAPI.
- Existing `forwardPrivate` performs actual uncached session checks, Origin/CSRF enforcement for mutations and signing; register exact method/path/purpose allowlists at both boundaries. API independently checks signature/fresh nonce and live session/staff/tenant/security revision/role before reads, writes **or receipt recovery**. Adding a route never broadens an existing purpose wildcard.
- JSON snake_case; canonical enums match existing storage (`NEW_EXAMINATION`, `FOLLOW_UP`, `ROUTINE`, `MAIN`, `OPEN`, `EXACT_TIME`). Appointment status output retains exactly Booked, Waiting, In Examination, Completed, Cancelled, No-show. Event instants are RFC3339 UTC, dates `YYYY-MM-DD`, local configuration times `HH:MM`, EGP values decimal strings with two fractional digits on output. Never accept JSON float money or ambiguous naive timed instants.
- Success `200/201 {data,revision,event_id?}` with `Cache-Control: no-store`. Collections use `data:{items,next_cursor}` with server-capped stable tenant/filter-bound pagination. Detail/collection results are explicit role projections, not serialized SQL rows or automatic nested relations.
- Failure `{error:{code,message,request_id}}`: 401 invalid/unusable session; 403 current role/clinic denial; 404 non-visible/missing resource; 409 state/capacity/revision conflict (`CONFLICT`, `STALE_REVISION` or `IDEMPOTENCY_CONFLICT` using existing codes); 422 invalid schema/money/date/interval/unsupported fields; 429 only existing configured abuse controls; 503 required security/database dependency unavailable. No SQL, PHI, Doctor narrative, secrets, foreign IDs or invented retry time in errors. Deterministic policy/interval ineligibility is not a dependency outage.
- Extra-forbid **command-specific** typed schemas validate nested settings/discount/interval input. Reuse typed-body canonicalization/revision/error helpers; do not weaken the existing flat Patient field-projection helper to permit arbitrary nested clinical data. Known forbidden authority fields and unknown fields fail 403/422; no mass assignment.
- Tenant, actor, role, Doctor identity, Appointment status/classification/lane/number, computed eligibility/net, revisions, audit identity, Visit identity and confirmation authority are server-derived. IDs used as resource references, expected revisions, quote-comparison values and Owner-entered settings/discount choices are inputs, not grants of authority. Expected quoted amounts are equality preconditions only; never persist a client snapshot/total as authoritative.
- `Idempotency-Key` is **required on every Wave 2 mutation**: Appointment creation, pricing PATCH, schedule staging/preview/activation, Visit eligibility PATCH and extension POST. This design makes the existing recovery mechanism explicit; it adds no workflow. Scope is actual tenant+staff+operation+key with canonical typed body; fresh signed transport nonce on every retry. Reauthorize before receipt lookup; identical key/body returns only the original committed role-safe result, changed content 409. Mutations also require expected relevant revisions. No generic receipt-browsing endpoint is added. No Wave 2 key expiry/receipt purge is authorized; production retention remains OPEN-OPS-03 / Issue #18. Losing the key grants no safe new-key retry: use permitted resource reconciliation and remain blocked if the outcome cannot be verified.
- GET changes no business state. Availability/qualification reads are advisory; commit rechecks current eligibility under locks. An uncertain HTTP result is reconciled using the original authorized key/current state before another mutation, never a new-key blind retry.

POST preview also supports renewed review by submitting the proposed change against refreshed revisions.

## 3. Pricing and settings DTO rules

Preserve existing D-04 policy field names through explicit mapping; do not replace whole policies with arbitrary JSON. Revision output identifies each changed/current policy kind rather than pretending PRICE and FOLLOWUP have one revision. API bases/fixed discounts are nonnegative finite EGP decimal strings with at most two fractional digits; percent is a finite decimal string in [0,100] with no additional fractional-digit cap (spec CHK011). Existing request-size safeguards remain; no new percentage digit limit is introduced. Preserve the full accepted numeric value in quote and snapshot `discount_value` output as a decimal string; two-digit output applies to EGP money, not PERCENT. Never silently round/truncate percentage input or pass it through binary float. Reject forged totals, unsupported currency, negative/excess discounts and missing reason. Unset initial prices remain null; missing required current pricing denies confirmation, not a guessed zero price.

Discount input is an explicit `discount_type` NONE/FIXED/PERCENT, `discount_value` and `discount_reason`. NONE uses zero with no reason. FIXED/PERCENT require a nonblank reason, including the full-base/100% discount representing a discretionary non-Urgent Free designation. Both booking roles may apply these to the applicable standard or preferential base with the same guards; no extra role-specific ceiling is approved. `is_free` is derived as `net_egp == 0`, including a configured zero preferential base with NONE. That zero base is explicit configured pricing, not an inferred unset price or a staff-entered Free discount, and NONE needs no discount reason. Against zero base, positive fixed discount fails; a valid percentage still yields zero and requires its reason. Do not accept a contradictory client net/free flag.

Server calculates exact intermediate Decimal deduction and rounds **only nonnegative final net** once to 0.01 EGP with ROUND_HALF_UP. Confirmed snapshot contains base, discount evidence, is_free/net, actual service classification, pricing version and creation standard base; preferential provenance has protected source/authorization references with only role-permitted operational output. Urgent enablement validates the general clinic calendar's operating periods and valid premium; standard-price publication cannot invalidate enabled Urgent. A schedule edit does not automatically disable Urgent or acquire a new blanket prohibition merely because it removes hours: later Urgent intake must independently reject missing/invalid hours, breaks and holidays. Every prospective Urgent discounted net must still exceed standard; no Urgent creation ships here.

CHK011 acceptance: reasoned `"12.345"` percent on `"100.00"` gives `"87.66"`; `"0.500000000000000000000000000001"` on `"1.00"` gives `"0.99"`, with the full percentage retained. Finite 0 and 100 are percentage-range endpoints, not exemptions from reason/Free/Urgent guards. Negative, above-100 or nonfinite percentages return 422 without successful effects; excess fractional digits alone do not. Arithmetic must retain accepted coefficient and fractional scale through final-net rounding, not round to a fixed default context first.

Legacy D-04 numeric/null JSON versions remain readable via database-text→Decimal conversion; new B-06 publication emits canonical strings through a compatible forward migration. Historical policy versions, seed defaults and confirmed snapshots remain unchanged. Owner settings cannot mass-assign Doctor clinical eligibility or ordinary staff permissions.

**Issue #20 Owner-approved compatibility exception (2026-10-29):** When a *current* D-04 numeric PRICE value cannot be represented exactly with two EGP fractional digits (e.g. `100.123`), the ordinary field is `null` rather than a rounded quoteable price. Only the Doctor/Owner receives an additional `legacy_price_remediation` object mapping affected PRICE field names to their exact plain-decimal numeric text (e.g. `{"standard_new_exam_egp":"100.123"}`); it is explicitly **remediation data**, not operational money. Receptionist responses and quotes never expose the object or original nonconforming number. A quote/confirmation depending on that field fails with the existing sanitized 409; independent canonical configured prices remain usable. The Owner explicitly corrects affected fields using the existing revision-checked, audited, idempotent pricing PATCH, which publishes a new PRICE version. Unchanged legacy numeric values in a partially corrected new version retain numeric JSON type and exact scale; only expressly corrected fields become two-decimal strings. Never rewrite historical versions or snapshots, silently round nonconforming prices, add an endpoint/UI, or weaken the standard operational DTO.

## 4. Calendar, slots and staged activation

- Proposed settings retain separately configured working days and optional positive daily/weekly work periods, breaks, holidays, explicit date overrides, manual slots and optional positive generated duration. No initial hours/duration/closing/cutoff or hidden Open cap. Preserve existing defaults and unrelated future-effective queue snapshots.
- Booking mode is clinic-wide for new bookings, with no date/period override or per-booking choice (spec CHK003 clarification). Mode changes preserve original confirmed Open/timed records; they may coexist historically on one date.
- Per spec CHK008, manual configuration supports weekly weekday sets and explicit date-specific replacement sets. A configured date-specific set replaces, never merges with, the weekly manual set for that date; an absent date-specific set inherits the weekly one. Preserve that distinction in typed schedule input/output. Resolve applicable calendar guards independently; manual selection never opens a closed date or resets generation. Only valid effective manual candidates suppress generated intersections. Both recurring and date-specific edits use the existing staged preview/activation path and preserve confirmed bookings.
- Per spec CHK007, generate from each applicable working period's start in positive duration-sized steps, offering only full intervals ending within that period. Omit break-intersecting slots without restarting/shifting later starts; discard any trailing remainder rather than offer a shorter slot. Apply valid-manual intersection suppression afterward. Availability and confirmation use this same grid; no additional generation-mode input or historical-booking rewrite is added.
- Per spec CHK006, overlap uses current saved CAPACITY directly, with no separately editable booking limit or additional numeric ceiling. Owner schedule reads return that integer and its CAPACITY revision as read-only context. Enabling requires configured Exact-Time slots and explicit confirmation of the current saved integer >=2 plus expected CAPACITY revision through staging/activation; confirmation values are equality preconditions, never CAPACITY writes. Missing/invalid confirmation or capacity 1 returns 422; stale expected capacity/revision returns 409 without activation. Availability supplies the applicable capacity revision; new booking includes/rechecks it with other relevant expected revisions and enforces current saved capacity. No capacity-setting route, implicit increase, historical-booking rewrite or admission approval is added.
- Explicit date override governs that date. Ordinary holiday/non-working booking OFF denies Open and Exact-Time. ON allows eligible untimed Open, but timed holiday opening still requires an explicitly applicable positive date-specific work period outside breaks; neither toggle nor manual candidate invents hours. Paid Urgent remains independently holiday-ineligible for its later intake owner.
- `no_show_cutoff` is exactly `{enabled:boolean,local_time:HH:MM|null}`, initially false/null. Enabling without a valid specified time fails. Saving configuration changes no Appointment state and starts no worker/cutoff workflow.
- Timed requests/candidates use offset-aware endpoints or explicit UTC instants resolving Cairo local input uniquely; retain `service_date`. Missing/nonexistent/ambiguous time without valid resolution fails. Validate both endpoints/positive UTC interval, applicable period/break/date and intended local date.
- Manual precedence suppresses all intersecting generated candidates, not just matching starts. All manual candidates still obey validity. Half-open endpoint adjacency is valid. Enabled overlap enforces actual peak simultaneous booking occupancy under locks, not total pairwise intersections; default overlap OFF denies any intersection.
- Preview binds clinic/actor/candidate, baseline schedule/day/record revisions and affected Open/timed bookings, plus counted-status contributors to a blocking timed-occupancy conflict; return only operational conflict data. Activation freshly checks complete affected set, including bookings on dates absent at preview, under the same schedule publication barrier used by booking. Any stale relevant revision requires renewed review; unresolved conflict cannot activate. No implicit cancel/reschedule/reprice, even if Wave 3 resolution is not yet available.
- Preview covers mode, manual slots, duration and overlap/effective timed-limit changes too. Existing confirmed intervals are not retroactively candidate-matched or rewritten. Under the approved 2026-10-28 Product Owner rule, proposed date/work-period/break invalidation blocks future `Booked` and `Waiting` (including a Waiting-only date), but does not retrospectively invalidate `In Examination` or `Completed`. Independently assess peak timed occupancy across all four statuses on every relevant future date, even with no `Booked` or no overlap-setting change; exceeding the proposed effective limit blocks activation. Preserve all existing statuses and intervals. An effective limit below existing peak occupancy conflicts, including disabling overlap with overlapping bookings. The effective limit is 1 with overlap OFF or current saved examination capacity with overlap ON; schedule DTOs accept no CAPACITY edit or separate booking limit. A cutoff change shows prospective exposure of still-Booked records to later reconciliation, including Open, but supplies neither a booking time boundary nor an immediate No-show; no worker is started. Distinguish affected review information from a booking actually made invalid.

## 5. Appointment creation and read projection

The client chooses a patient resource, day and intended service, not a tenant/Doctor/status/lane/number/authoritative price. Under the active clinic-wide mode, Open omits interval; Exact-Time supplies endpoints exactly matching a current valid manual or unsuppressed generated candidate. Validate membership and interval/capacity again at commit, never treat prior availability as a reservation. New booking rejects a past Cairo service date and a timed start already passed today, evaluated at confirmation; no added minimum advance duration. Per spec CHK002, neither `GET /api/slots` for a requested service date nor new Open/Exact-Time confirmation imposes a maximum future horizon. Otherwise valid dates 366 and 3,650 Cairo days ahead are allowed examples, not limits; calendar/slot/capacity/price/access guards and preferential Follow-up deadlines still bind. No new horizon setting or bulk future-slot generation is added. Existing committed receipt recovery is not new booking. Current ordinary eligibility applies equally to New Examination and qualified Routine Follow-up.

`expected_source_revision` is the reviewed source Visit's `clinical_revision`, returned as operational `source_revision`. A B-10 confirmation referencing `source_visit_id` must supply this nonnegative integer (missing/invalid → 422); without a source, it must be null/omitted and no unreviewed source is automatically selected. After live authorization and receipt resolution, acquire patient/policy locks and allocate the service-day number/counter lock before source Appointment→Visit→claim locks. Check source visibility first, preserving non-oracular 404; compare the expected revision under those locks **before either preferential qualification or acknowledged fallback**. A mismatch returns `409 STALE_REVISION` with no committed effects, including no number assignment or success receipt. Include the field in the canonical typed-body digest. Identical committed receipt recovery still precedes new-work revision checks.

Booking staff can obtain current permitted bases/revisions and a server-calculated quote from the pricing read above. New confirmation requires expected applicable PRICE/FOLLOWUP/SCHEDULE/source revisions, CAPACITY revision for enabled timed overlap, and expected quoted base/net; compare to current locked state, current saved capacity and recomputed price. A stale revision or different quoted value returns sanitized `409 STALE_REVISION`/`CONFLICT` and commits nothing, even if the newly calculated amount would be valid. Refresh/review before new confirmation; do not silently substitute current prices. Matching requests freeze exactly the quote reviewed. A previously committed identical key/body instead returns its original authorized receipt, unaffected by later price/schedule/capacity changes.

Return Booked, MAIN/ROUTINE, actual service type, immutable number/assignment, frozen EGP evidence and revision. Both roles can see authorized operational booking/discount data. Never expose Doctor-authored Visit content via history/populated source, preview, receipt, search or error. Archived existing-ID operational context remains narrowly purpose-bound; it grants no general Receptionist archived Patient read/write. New-ID creation remains denied for archived patients.

Expected material conflicts include same-patient counted day, occupied/oversubscribed timed interval, stale policy/source revision and active source claim. Use sanitized 409 and refresh, not client-forced override. Cancelled/No-show allow a distinct eligible new ID/number; Completed remains counted. Walk-in OFF and Pause do not deny ordinary Booked-only creation or justify booking+attendance fusion.

## 6. Follow-up qualification and fallback

Qualification reads in the permitted booking context expose an explicit Receptionist field allowlist: `patient_id`, `intended_service_date`, `requested_service_type`, `actual_service_type`, `preferential_available`, permitted `source_visit_id` (or null), operational `source_revision` concurrency token (or null), applicable price/schedule revision tokens and the operational `price_quote` fields defined in §2. Source IDs are references, never general Visit-read grants. Doctor may additionally see protected own-clinic decisions through the authorized B-10 context. Receptionist receives **no** raw `followup_decision`, source/extension deadline, Doctor justification, source clinical fields or protected clinical audit; derived availability is not the Doctor record. Absence of a candidate does not disclose hidden Visits. Existing Appointment details expose operational reservation linkage, not populated source content.

| Condition checked inside confirmation | Result |
| --- | --- |
| Same patient/Doctor/clinic Completed Routine/Emergency/Urgent New Examination, recorded Doctor eligibility, intended day within authorized window, no active/consumed claim | One preferential Routine Follow-up with frozen source/deadline/authorization/price and ACTIVE claim. |
| No selected qualifying source, accessible but uncompleted/wrong qualifying type/opted out/expired, missing recorded Doctor decision, or source already consumed | NEW_EXAMINATION only, under ordinary current price and every normal booking guard, **after** the acknowledgment/discount reaffirmation below. Without it, 409 without booking effects; refresh permitted qualification/pricing reads. Never label it a standard-price Follow-up. A same-patient/Doctor relation mismatch cannot authorize preferential care. |
| Source already actively reserved | 409 conflict, no automatic fallback or second preferential claim, including different target dates. |
| Explicit missing/foreign/non-visible source reference | Non-oracular 404; no fallback mutation or source details. |
| Archive, counted day, current role/tenant or slot/date failure on either branch | Deny under the corresponding ordinary contract; fallback cannot bypass it. |

The default intended deadline is source **completion Cairo date + seven calendar days inclusive**. Per spec CHK013, a Doctor-specific exception requires a specific date on/after source Cairo completion and recorded justification; it may shorten below day seven or extend beyond it, with no maximum duration. Before-completion deadline values or missing justification return 422 without changes; unauthorized writers remain denied. Expected source revisions and protected audit still apply. A source-decision edit cannot reduce confirmed entitlement; a confirmed-target extension remains separate, prior, justified and non-shortening, preceding any later B-18 outside-deadline move. Later policy opt-out/shortening/prices cannot invalidate confirmed entitlement; new booking after valid terminal release requalifies with current policy/price. Recommendations and extensions never automatically book/move.

Per spec CHK014, day-zero intended service is eligible: source Cairo completion date <= intended date <= authorized deadline, with source already Completed at confirmation. Earlier dates never qualify, even under Doctor exceptions/extensions; any ordinary fallback still requires acknowledgment and all ordinary guards, including past-booking rejection. Same-patient/day uniqueness uses original/current Appointment service dates, not the source completion date. A source Completed on its own target service date blocks another counted appointment there (409); an older-service-date source finishing today may qualify for today if no other counted appointment or ordinary guard blocks it. No clinical source date or content is added to the Receptionist projection.

Per spec CHK035–036 Product Owner answers, fallback acknowledgment binds actual NEW_EXAMINATION, ordinary base, final net, submitted NONE/FIXED/PERCENT choice/value/reason and current applicable revisions. Staff must explicitly choose or reaffirm that discount, including NONE; previous Follow-up inputs remain available for review, never silently transferred or cleared. The ordinary server-calculated quote can be read through §2 without claiming entitlement. `discount_reaffirmed:true` records acknowledgment intent, not discount authority: the server independently revalidates permission, discount and source/date/slot/current quote. If a later source/price/schedule change invalidates this reviewed result, return 409 with no booking effects and require refreshed review. An unchanged request already carrying valid acknowledgment may commit in one confirmation; no mandatory new endpoint, token service or UI is added. Denied attempts create no success receipt; a changed request may reuse its uncommitted key, but any committed key with changed content conflicts under §1.

## 7. Deliberately absent interfaces

No intake/check-in/queue/projections/reorder/Pause/capacity/confirmation issue-revoke/admission API, general clinical editing/completion/exceptional cancellation, individual cancellation/replacement/reschedule, bulk/reconciliation/No-show/day-close, worker invocation, notification delivery/SSE/push, files/export/reports or UI is added. Existing later master routes remain closed until separately authorized. No generic status PATCH, lifecycle test route, bulk cancellation, payments, public registration, patient messaging, E-Prescription or commercial interface.

Required validation/evidence is in [quickstart.md](../quickstart.md): both authorized staff roles, Owner/Doctor-only denials, route/purpose tampering, CSRF, foreign resources, field projection, live revocation/receipt recovery, atomic failure and real PostgreSQL races. Synthetic passing evidence does not choose production policy values or authorize release.
