# Wave 2 Data Model

Phase 1 design, not executable DDL. Sources: [spec.md](spec.md), master §§2/7/11.4 and Domain §§3–11. [Research](research.md) records choices; [transactions](contracts/transactions.md) records lock/atomicity boundaries. Logical new names are implementation design, not new product resources.

## Shared representation and security

- Reuse immutable application UUIDs and existing native Better Auth identity/session types. Clinical rows require non-null tenant identity, unique tenant/ID keys and tenant-qualified foreign keys; verify patient/Doctor/Appointment relationships, not just independent valid IDs. No clinical cascade deletion.
- Event/expiry/admission/completion instants are UTC `timestamptz`; Cairo service/deadline dates are `date`. Clinical evidence records actor/actual role and at least second-precision time. Never derive service day by truncating UTC or move it at midnight.
- Server-incremented revisions and expected-revision checks apply inside locked writes. Preserve exact Appointment labels: Booked, Waiting, In Examination, Completed, Cancelled, No-show. Queue/claim/approval/review dispositions are not extra Appointment states.
- All new clinical tables use FORCE RLS read/write checks, non-owner NOBYPASSRLS runtime, no-context denial and no operator clinical grants. Protected Doctor content has stronger field/access guards than operational data. Only the migration role owns DDL.
- Use existing B-01 `protected_transaction`/`AuthorizedStaff`, which establish `app.staff_id` after live authorization. Doctor write/audit guards resolve that actual staff identity against current staff/clinic/Doctor linkage and security/reset-block conditions, following the existing `guard_clinical_audit` pattern. Do not trust an `app.role` string, request actor or fabricated old/new JSON. This is the existing trusted runtime credential boundary, not a claim that a malicious holder of that credential cannot forge a custom GUC.
- Connection-taking persistence primitives establish lock order before writes; deferred constraint checks inspect final current rows and do not acquire late upstream locks. Revoke update/delete and install immutable-evidence guards as appropriate. Operational receipts/outbox must not contain clinical narratives or protected before/after values.

### Policy/monetary compatibility

Initial prices remain null/unconfigured. New B-06 publication accepts/emits finite decimal strings; use a forward-only evolution of the existing PRICE validator to retain historical numeric/null versions while validating new string versions. Parse legacy JSON numbers from database text into Decimal, not binary floats. Retain old policy bytes/identities and references. Add representative old/new policy upgrade/read tests and keep D-04 seed defaults valid.

Nonnegative two-digit EGP bases/fixed discounts; finite percentage in [0,100]; required nonblank reason for FIXED/PERCENT, no reason/value for NONE except zero value. Both booking roles may discount standard or preferential bases under the same guards. Discretionary Free non-Urgent is a reasoned full discount, not an independent contradictory total. Snapshot `is_free` is derived from zero final net, including a configured zero preferential base with NONE; that configured base is neither unset nor a discretionary discount and needs no discount reason. Positive fixed reduction against zero fails; a valid percentage remains zero and needs its reason. No Free Urgent. Use adequate Decimal precision and one nonnegative final-net ROUND_HALF_UP; Urgent base and rounded net must exceed current standard base. Enablement requires valid general-calendar periods; subsequent calendar edits need no automatic toggle change or blanket ban, but confer no later intake eligibility when periods are missing. Future changes never reprice.

Spec CHK011 imposes no additional percentage fractional-digit cap within existing request-size safeguards. Reuse D-05's unconstrained NUMERIC `discount_value`, preserving the full accepted numeric value; money remains two-digit EGP, but PERCENT must not be quantized to that scale. Quotes, snapshot validation/persistence and serialization must round-trip that value without binary float or precision loss. Exact arithmetic must accommodate accepted coefficient and fractional scale before one final-net rounding; a fixed default precision is not a substitute. Preserve existing snapshot values and guards; verify US2.7's ordinary/high-precision examples and zero/100/invalid boundaries during B-06, not by changing historical snapshots or introducing a new storage representation.

Cutoff remains `{enabled:false, local_time:null}` initially. B-07 rejects enabling without an explicit valid Cairo-local HH:MM; it neither guesses a time for historical storage nor treats work-period end as cutoff. Stronger operational validation applies to new publication without rewriting old versions.

### Appointment and timed validation

Retain partial counted uniqueness `(organization_id,patient_id,service_date)` for Booked/Waiting/In Examination/Completed. Cancelled/No-show permit a distinct new ID; Completed blocks. Open has null endpoints and no time-derived cap. Timed requires both positive canonical instants, intended Cairo date and valid applicable periods/breaks/date rules; gap/fold input resolution is in [research §4](research.md#4-interval-capacity-and-cairo-time). Actual counted timed occupancy is transactionally checked against configured overlap capacity; an exclusion constraint alone cannot implement capacity above one.

Spec CHK001/003/021 answers govern new confirmation: reject past Cairo dates/passed starts today; use the one active clinic-wide mode and exact current manual/unsuppressed generated candidate endpoints. Preserve prior Open/timed records across mode/slot changes without retroactive candidate matching. Per the approved 2026-10-28 Product Owner decision, schedule date/work-period/break invalidation is blocking for future `Booked`/`Waiting` (even on Waiting-only dates), but does not retroactively invalidate `In Examination`/`Completed`; original dates, states and intervals are retained. Preview every affected slot/mode/duration/overlap change; count all four timed statuses in peak occupancy on relevant future dates, even with no `Booked` or change to overlap settings, and block a proposed effective limit below current peak, including disabling overlap with overlapping bookings. The effective limit is 1 with overlap OFF or saved examination capacity with overlap ON, not a separate setting. Price/schedule/source revisions and reviewed quote are comparison preconditions; stale new work fails, while committed receipt recovery retains the original snapshot. Clinic/day number uniqueness/non-reuse is not a gapless guarantee. Cutoff review shows prospective still-Booked reconciliation exposure; it does not introduce an interval boundary or change state.

Spec CHK002 explicitly excludes a maximum future booking horizon for Open/Exact-Time availability and new confirmation. No horizon column, setting, expiry or pre-materialized future slot series is added; evaluate the requested valid service date under current guards. Preferential Follow-up still enforces its authorized deadline and all ordinary guards. This changes neither retained service dates nor later-wave existing-ID workflows.

Spec CHK006 uses existing CAPACITY policy directly for enabled timed overlap, not a separately editable SCHEDULE booking limit or duplicate capacity field. Enabling requires configured Exact-Time slots and Owner confirmation of the current saved integer capacity >=2 and its revision. The confirmed value is a comparison precondition, not a capacity write; no additional numeric ceiling is approved. New booking reads/rechecks current saved capacity under policy locks. Preserve historical policy payloads and existing bookings; capacity-changing commands remain B-14, and booking does not consume or supply an admission confirmation.

Spec CHK007 anchors generation to each applicable working period's start, advancing in positive duration-sized steps. Keep only full intervals ending within that period; omit break intersections without restarting or shifting the grid, discard trailing remainders and then suppress intersections with valid manual slots. Derive candidates from the current schedule rather than persisting a second grid; existing confirmed intervals remain unchanged.

Spec CHK008 uses the existing weekly/date-keyed interval representation for weekly manual slots and explicit date-specific replacement sets. Preserve whether a date-specific set is configured: its presence replaces that date's entire weekly manual set; absence inherits the weekday's weekly set. This is manual-set selection, not a work-period override, union, inferred opening or generated-grid reset. Apply the resolved date/work/break/holiday guards before effective valid manual candidates suppress generated intersections. Reuse schedule versions/preview and preserve existing intervals.

## D-06 — QueueDay, QueueEntry and Doctor admission foundations

| New record | Essential fields | Relationships / validation |
| --- | --- | --- |
| QueueDay | Tenant/ID, Doctor, original `service_date`, `lane` MAIN/EMERGENCY, revision, effective QUEUE policy reference, arrival counter, MAIN Routine cursor. | One partition per clinic/date/lane (single clinic Doctor); tenant-qualified Doctor/policy. Date snapshot immutable for active day; later policy does not silently reorder it. EMERGENCY does not own/advance MAIN cursor. |
| QueueEntry | Tenant/ID, QueueDay/Appointment/patient/Doctor, original date/lane, server arrival sequence and attestation actor/time, Routine rank when applicable, active/closed disposition, closure/attendance-history reference, revision. | Partial unique active tenant/Appointment; unique partition arrival sequence and valid active Routine ranks. Initial arrival/presence evidence retained on close; rank is not the booking number. Deferred matching checks apply to active membership only, so later reschedule cannot rewrite historical dates. |
| DoctorControl | Tenant/Doctor identity, synchronization revision and reference to current D-04 CAPACITY policy/relevant control revisions. | One shared row across every service date/lane, locked before queues. Existing CAPACITY policy remains authoritative for Pause/capacity; no independently editable duplicate settings or active-count cache. Initialize for existing/future tenants through the established narrow initialization pattern. |
| DoctorAdmissionConfirmation | Tenant/ID, issuer/Doctor/patient/target Appointment, original date/lane, issued/expires instants, captured Appointment/QueueDay/control/CAPACITY/authorization revisions, ISSUED/CONSUMED/REVOKED, consuming admission-history reference/time, revoke evidence. | Exact same-tenant/Doctor/patient target. Doctor-only issue/explicit revoke; unused valid confirmation consumed once with matching admission/history/queue closure. Expiry and stale invalidation derived; equality at expiry is unusable. No blanket grant or production TTL. |

Deferred checks on **both** Appointment and QueueEntry changes enforce final-state equivalence: Waiting has exactly one active entry matching tenant/Doctor/patient/original service date/lane; every non-Waiting record has zero. Check current final rows, not an earlier trigger NEW image. Unique-active alone cannot enforce existence or correct matching. Preserve inactive history instead of a date-qualified FK to the Appointment's mutable current service date.

Use the shared Doctor control lock and current D-05 `In Examination` Appointment count across all dates/lanes to enforce the capacity boundary in persistence simulations. Approval consumption references the immutable D-05 `Waiting → In Examination` admission-history revision; it does not require a Visit FK. Cursor may advance only with ordinary MAIN/Routine-head admission evidence, never Emergency/Urgent/Doctor exception, cancellation or reorder.

QueueDay creation must snapshot the effective policy for its original approved service date. Open attendance may create a dated partition without inferred hours/end time; an absent calendar leaves appropriate pending policy effectiveness rather than inventing an operating day. No creation happens from ordinary booking. Actual check-in/ordering/issue/revoke/Pause/admission commands remain B-12–15.

## D-07 — Visit and immutable clinical revision

| New record | Essential fields | Relationships / validation |
| --- | --- | --- |
| Visit | Tenant/ID, unique Appointment, patient/Doctor, original service date, D-05 admission-history reference, admitted instant, clinical revision; structured examination/findings/diagnosis/medical_notes/treatment/tests and recorded eligibility decision/provenance. | Unique tenant/Appointment; tenant-qualified link to that Appointment's real Waiting→In Examination history, patient and Doctor. Retain after exceptional cancellation; completion instant/evidence derives from the actual Completed transition, not service date. No independent Visit status enum or fabricated admission. |
| ClinicalRevision | Tenant/ID, Visit, revision/change kind, immutable OLD/NEW values, actor/actual role, second-precision event instant and required reason, source-decision/extension provenance where applicable. | Protected append-only evidence generated/checked against actual guarded changes. Doctor identity must match live authority and Visit Doctor; no client-chosen audit identity or unverified before/after. No operational response/outbox narrative. |

D-07 checks alone rely on D-05, not QueueDay/confirmation. Deferred checks require exactly one Visit after a genuine admission; Booked/Waiting have none. Completed/admitted exceptionally Cancelled retain that same Visit; cancellation without admission and No-show cannot manufacture one. A structural Visit shell INSERT is permitted for either live staff role as the actual actor of genuine matching admission history, under tenant/RLS checks; it requires NULL clinical fields/decision and revision 0. This does not require a Receptionist actor to be the Visit's Doctor. Clinical UPDATE remains Doctor-only with protected old/new revision/audit evidence; structural insertion grants no clinical authorship. Operator, inactive/foreign staff, missing context, forged admission linkage and clinical content on INSERT are denied. Admission policy/head/Pause/capacity command validation remains B-15; no operational command is added. A status value alone is insufficient admission proof. Reject duplicated/mismatched admission references and prohibited terminal Appointment changes. Doctor terminal clinical corrections append immutable old/new evidence while preserving Appointment terminal state/history.

B-10 may write only source eligibility/justified exceptions/extension evidence; general Visit documentation/completion/cancellation/correction commands stay B-16, and operational admission stays B-15. Persistence-level corrections are tested with valid synthetic records now. Clinical read/write restrictions reuse actual staff role validation, not arbitrary database GUC role labels.

## D-08 — FollowUpClaim as reservation and durable completion ledger

| New record/evidence | Essential fields | Relationships / validation |
| --- | --- | --- |
| Retained FollowUpClaim | Tenant/ID, unique preferential Appointment, patient/Doctor, original source Visit/Appointment, frozen current clinic FOLLOWUP policy revision, source-decision revision/Doctor clinical eligibility, any **date-specific new-booking exception's authorizing actor/role/optional Receptionist reason and immutable audit reference**, completion-local date, approved date/deadline, immutable price-snapshot link, lifecycle ACTIVE/RELEASED/CONSUMED, terminal-history reference/time. | Tenant/patient/Doctor and source relationships agree. Only Completed New Examination source; preferential target is Routine Follow-up with matching frozen provenance. Never delete released claims or mutate consumed evidence. No Receptionist clinical Visit edits. |
| Doctor extension evidence | Tenant/ID, source Visit and exact confirmed claim/Appointment target, prior preserved deadline, extended deadline, issuing Doctor, reason/time, expected source/claim revisions and protected clinical audit reference. | A distinct prior justified authorization; extension cannot shorten the preserved deadline, reprice, reschedule or reopen. Original snapshot remains unchanged; later permitted reschedule consults extension history. |

Choose the smallest durable ledger: retained claims with **unique source across ACTIVE or CONSUMED** rows, excluding RELEASED history. This enforces at most one active claim, at most one permanent consumption **and no active reservation alongside a consumed source**. Separate unique-active/unique-consumed indexes without that cross-state exclusion are insufficient. No duplicate consumed flag/table is needed.

Qualify under source Appointment→Visit/claim locks even if no claim exists. Source must be same clinic/patient/Doctor, Completed Routine/Emergency/Urgent New Examination with Doctor eligibility. Completion-local date is day zero; inclusive default deadline derives from the **currently effective Owner-configured FOLLOWUP policy** (initially date + seven calendar days), including after release. A Follow-up or exceptionally cancelled Visit cannot source entitlement. Doctor source default/exception decisions and booking read the same source revision. A reviewed source reference requires `expected_source_revision`, equal to the source Visit's locked `clinical_revision`, before either preferential or acknowledged fallback confirmation; stale requests fail with no committed effects. Booking takes the day-counter lock before source Appointment→Visit→claim locks. No source reference means ordinary acknowledged fallback without implicit preferential source selection.

Spec CHK013 permits a justified Doctor-specific deadline on/after the source Cairo completion date, including shortening below day seven or extending beyond it, with no maximum duration. Store a specific date and protected Doctor justification/revision; reject dates before completion. Source edits affect fresh qualification, never an existing claim's frozen entitlement. Confirmed-target extension evidence remains separate, prior and non-shortening.

**Approved 2026-11-03 amendment, pending implementation (Issue #24):** A Doctor **or** an authorized Receptionist may approve a particular **new-booking** date outside the Owner's clinic-default window. The Receptionist does so independently without changing Doctor-authored `followup_decision`; Receptionist reason is nullable while a **tenant-scoped immutable audit is mandatory** even when null. Preserve source/role identity, source and effective policy revisions, selected date, authorization timestamp, and resulting confirmed claim linkage; never expose clinical narrative to Receptionist. Existing D-08 `0022_d08_followup_claims` hard-codes DEFAULT to +7 and does not yet represent this exception: implement the amended invariant by a reviewed **new forward-only migration** if schema/guards require it, never by rewriting the published revision. The historical D-08/B-10 design and CI remain evidence for the old contract only.

Spec CHK014 qualifies intended dates from source Cairo completion day zero through the authorized deadline inclusive; pre-completion dates never qualify, even under exceptions/extensions. Source must already be Completed at confirmation. Counted patient/day uniqueness still uses Appointment service dates: a Completed source on the target service date blocks another appointment, whereas an older source service date completing on the target date does not itself occupy that day's allowance. Apply every ordinary date/start/slot/archive/authorization guard; completion date never rewrites the source service date or overrides uniqueness.

A missing recorded Doctor decision does not imply eligibility (master B-10). A permitted New Examination fallback creates no claim and requires explicit actual-type/ordinary-price acknowledgment and discount reaffirmation under spec CHK035–036; recompute against locked current policy and reject stale evidence without writes. Do not persist client quote amounts as calculated price or treat an acknowledgment as Doctor authorization. The existing receipt/history/snapshot evidence records the actual operation; no separate fallback ledger is needed.

| Target Appointment outcome | Required final claim state/evidence |
| --- | --- |
| Booked / Waiting / In Examination | ACTIVE; exactly one matching claim for every preferential Appointment. |
| Cancelled / No-show | RELEASED, with matching terminal history in the same commit. Includes exceptional In Examination cancellation retaining Visit. |
| Completed | CONSUMED with immutable completion history in the same commit; source permanently unavailable. |

Check both Appointment→claim and claim→Appointment relationships at commit, including target classification/provenance, source linkage and terminal-history binding. A failed outcome cannot release/consume. Future opt-out/policy shortening does not invalidate an already confirmed frozen claim; later new claim after RELEASED requalifies at current price/decision. Busy ACTIVE reservation conflicts; absent/nonqualifying/consumed entitlement uses New Examination under ordinary guards, with explicit non-visible IDs denied before fallback.

These are D-08 foundations; B-16/B-17/B-20 later own actual completion/cancel/No-show commands, and B-18 owns deadline-aware reschedule. Do not expose a lifecycle PATCH or fixture endpoint.

## D-11 — DayReview and indexed query foundations

| New record | Essential fields | Relationships / validation |
| --- | --- | --- |
| DayReview | Tenant/ID, original service date, current revision, review/final-close disposition, actor/time, retained review/amendment evidence reference. | Unique clinic/day current review; expected-revision updates, immutable old/new review history through existing audit. Final close serializes with same-date attendance/membership changes across **both lanes**, using an existing policy-tier barrier before absent QueueDay creation and dated rows. It requires no unresolved Waiting; it does not terminate In Examination, convert Booked to No-show, cancel/migrate a queue or impose a closing time. Reuse the existing tenant/phone/ID family index and D-05 current/historical assignment paths. Completed service value joins frozen net to **Completed Appointment** (not all retained Visits), attributed to original service date; activity uses event dates. No D-08 requirement, materialized analytics, report API, retention/volume/latency rule or reconciliation command.

## Migration evolution and affected consumers

- Append after `0018_d05_appointments` through one writer; actual revision filenames/order are selected during authorized task execution, not reserved by new masters. Preserve published migrations. Each owner references only its direct dependency tables; D-06 and D-07 remain independently verifiable. Integrated-head fixtures satisfy all installed guards; dependency-revision simulations may verify independent foundations.
- New constraints/triggers do not automatically prove untouched historical rows valid. **Explicitly preflight/validate existing rows.** D-05 accepted synthetic Waiting/In Examination/Completed fixtures without the future queue/Visit evidence. Never silently grandfather inconsistent rows or fabricate arrival/admission/clinical history: incompatible historical data must safely reject the upgrade, retain prior state/version and await separately approved remediation. For D-07, successful immediate-predecessor fixtures contain no prior admission (Booked/Waiting/No-show and pre-admission Cancelled, satisfying installed guards); `visits` does not exist before its introducing migration. Legacy In Examination/Completed or admitted exceptionally Cancelled rows without required evidence must safely refuse, never trigger fabricated history/backfill. Cover all six statuses after installation using legitimate evidence. Use compatible synthetic predecessor rows for successful upgrade proof and incompatible fixtures for safe-failure proof.
- Every new migration affecting existing objects gets a representative populated **immediately preceding revision** upgrade test plus fresh/repeated upgrade/failure rollback. Assert IDs, policy versions, snapshots, counters/assignments, receipts, clinical/history links, original dates, FORCE RLS and actual runtime/operator grants survive. Issue #13's older historical rehearsal is separate.
- Adapt D-05 direct-status fixtures to legitimate new memberships/admission/history/Visits at integrated head while preserving their original money/uniqueness assertions. Do not remove denials to make a new trigger pass or import later operational commands just for setup.
- Update SQLAlchemy metadata, API/Web compatible-head readiness (worker shares Python readiness), schema/health/failure-migration tests, protected route/purpose allowlists and `ops/check.ps1` CI suite registration together. Review any necessary privileged function/view/grant with fixed safe search_path and narrow EXECUTE; never add bypass privileges solely to simplify tests.
- [Quickstart](quickstart.md) defines positive/denial/race/failure/query-plan evidence. No schema or behavior is claimed verified by this model, and production policy gates remain open.
