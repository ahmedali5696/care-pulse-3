**Status**: Phase 1 design; no executable acceptance. Applies to [HTTP contract](http.md), [data model](../data-model.md) and approved plan §§2/9/11.4.

## Identity and Effective Privileges

Every new browser-facing operation must have synchronized BFF method/path/purpose signing, API `ClosedServiceBoundary` registration, database `f01_private.route_purpose`/target parsing, stage/capability checks, effective grants/RLS and response projection. Use the canonical private route/method/purpose inventory in [HTTP](http.md) as the single mapping, including phase and status purposes. These are planned registrations, not current grants.

Bind target patient/attachment/export/artifact/device/recipient and allowed query/body scope. A generic authorized staff transaction cannot confer export-only full narrative reads or direct unrestricted file tables. Use narrowly scoped database functions/projections for export/report/event purposes and tenant-qualified storage access. Public download GET to private POST and private stream batch translations must be registered explicitly. Exact raw binary and JSON bodies remain independently verified.

B-23 owns narrow actual-`carepulse_worker` login capabilities for enumeration of nonclinical tenant IDs and tenant/event/consumer/claim generation, following B-20's actual-login capability pattern. B-25 consumes B-23's enumeration capability for notification orchestration without duplicating it; B-20's existing cutoff capabilities remain unchanged. No staff impersonation, global clinical SELECT, migration credential, inherited bypass or GUC-only authority. The metadata sender retains its existing `carepulse_sender` identity; operator remains clinically denied. Use fixed definer search paths/ownership and revoke PUBLIC/unneeded effective grants.

## Multi-transaction F-01 Authorization Lifecycle

Use **fresh independently signed private requests for each protected physical transaction**, each registered once and bound once to its own PRIMARY. Business phases below are persisted operation states, not new values passed to `f01_bind`. Existing F-01 does not authorize arbitrary PREPARE/PUBLISH/REDEEM stages. Never reuse PRIMARY, transfer a request binding to another PID/xid/login, or use invitation/session-cleanup/receipt-recovery stages as continuation authority.

The BFF orchestrates these short private calls behind the existing public operation. Immediately before every call it verifies the current session, derives current actor/tenant/security revision and signs a fresh timestamp/nonce and exact target/query/body. API registers proof independently, obtains a fresh gate binding for that physical READ COMMITTED transaction, activates it and rechecks live staff/session/resource authority. Each private phase route/purpose and its database-parsed command/target must be narrowly registered in a future forward-only migration. No phase route or new privilege exists merely because it is named here.

| Public operation | Separate protected transactions, each with a new proof | External interval and final fence |
| --- | --- | --- |
| Attachment upload, each chunk | Raw binary upload reserves the exact position and chunk identity; independently signed publication commits its metadata and progress; separately signed read-only upload status reconciles a lost/unknown result. | Stage immutable exact bytes outside locks. Publication rechecks live authority, target, operation/key, expected revision, generation/claim/lease, offset, length/digest, whole-file binding and quota before CAS. No acknowledged progress until committed publication. |
| Attachment finalize | Reserve current staged generation; later publish the verified candidate under a new signed phase call. | Scan/encrypt immutable staged bytes outside transactions. Publish rechecks live permissions, class/policy/Visit, operation digest, expected revision, generation/lease and candidate digest before CLEAN/audit/receipt commit. |
| Export creation | Reserve logical operation; extract one full-record statement snapshot in a separate fresh authorized read; publish both artifacts in a later fresh authorized transaction. | Render/encrypt captured snapshot outside locks. Extraction records its snapshot/source identity against the same operation generation. Publish verifies that identity, both artifact digests, actor/session, patient, purpose, preparatory creation verification and current generation before READY/audit/receipt. READY may have zero grants. Issuing either artifact grant requires separate positive handoff confirmation matching the intended recipient. |
| Download | Fresh authorized preflight pins exact immutable artifact and an unconsumed grant; a separate fresh authorized redeem transaction follows authenticated decryption. | Preflight does not consume grant or authorize later disclosure. Redeem rechecks session/class/tenant/artifact digest and revision, original grant expiry/unused state and preflight generation; atomic CAS consumes/audits before serving. A second preflight cannot create a second redemption. |

Use the narrow private subroutes in the HTTP inventory, including upload publication/status, finalize prepare/publish/status, export reserve/extract/publish/status and download preflight/redeem/status. Export reserve is the first private phase of the existing public create operation. Download public GET still translates its bearer into signed private JSON. The BFF's original authenticated public request or a server-generated operation handle is not continuing authority: every subcall must independently pass the complete identity boundary. Private candidates/handles contain no reusable authorization; bind immutable server-generated `StagingAttempt.attempt_id` UUID through tenant-qualified identity and references to the exact operation, owner, phase and generation, alongside persisted tenant, actual actor/session/security revision, operation/key/target/body digest, phase, expected revision, attempt generation/claim/lease and immutable inputs/results. File calls verify the signed effective `policy_digest` against independently loaded policy per HTTP, including the initial status check before BFF spooling and each subsequent phase. Reject wrong phase, skipped prerequisites, cross-actor/session/target, duplicate or stale publication and cleanup-owned candidates. An idempotent completed phase returns only its saved authorized result, never repeats its effects.

Proof lifetime remains unchanged: registration uses signed issuance plus configured freshness, not time since scan completion; binding rejects expired or clock-regressed requests, activation is limited by proof and live session horizons, and `f01_context()` stops exposing authority at activation expiry. A lock wait can exhaust this horizon. Fail closed and roll back a phase if authority expires before its protected work completes; do not refresh `valid_until`, increase freshness/skew, retain a transaction over external I/O or sign using an old captured session. Complete external work while its candidate lease is valid, then obtain a new proof for publication; expired proof never becomes an expired grant's extension. Required future writers must check valid context at their authoritative writes/completion guard, not only at initial activation.

Recovery uses a new signed, specifically registered **read-only status/receipt request**, itself a new PRIMARY binding, scoped to the same authorized actor/session/tenant/operation/key/target/digest and generation. Read back committed state before any new mutation after unknown commit. If prior xid is still in progress, wait/reconcile without a competing publish; if committed, return its valid saved projection; if aborted/not applied, resume only the permitted phase under fresh proof and current generation. An unresolved result remains UNVERIFIED/non-readable. After crash, expired lease or cleanup claim, fence stale attempts and reprepare a new generation only after reconciliation. Lost redeem acknowledgment leaves a committed grant consumed and never re-serves bytes on retry. Existing RECEIPT_RECOVERY remains only its exact allowlisted aborted-primary read-only path; do not extend it implicitly to these workflows. No cached proof, worker bypass or receipt itself supplies fresh staff authority.

## Lock and Receipt Rules

Retain approved order for applicable domain rows: tenant/live permission → Patient lifecycle → policy/service-day → Doctor capacity → QueueDay → Appointment(s) → claim/confirmation → append history/audit/outbox. Existing originating commands keep their current validated order; consumers do not reacquire unrelated domain locks or rewrite transitions.

For all new protected phases use the existing F-01 per-Organization authority barrier first (same barrier as staff disablement, grant changes and tenant suspension; no parallel authorization lock). Under that barrier acquire applicable live staff/session/security-revision/grant authority rows before downstream rows, in stable staff/session ID order if multiple are needed. Privilege writers follow the same authority-first order; preserve native session invalidation and verify its actual ordering with the live authorization barrier. File/export phases then lock Patient lifecycle → applicable upstream Appointment(s) → Visit(s) → Attachment/Export owner → PrivateObject/artifact → attempt/generation/quota reservation → DownloadGrant, only applicable rows and stable IDs within each group, then append audit/receipt. Preserve the relative upstream policy/day/control/lane/Appointment/Visit order where applicable; do not acquire these locks late through FK/trigger paths. Cleanup uses the same prefix/order with its narrow worker capability; neither cleanup nor grant redemption may acquire authority after taking a downstream lock.

Notification claims take the tenant authority/capability barrier before event claim rows and commit the lease without retaining locks. Publication in a fresh transaction takes that same authority barrier → recipient live staff/grant authority in stable recipient ID order → source event/delivery claim and generation → TenantStreamState → recipient notification rows in stable key order → audit/outcome. Recheck eligibility and generation after acquiring locks and before publication. Never hold an event/stream lock while waiting to acquire live authority; never reverse the order on retry, replay or terminal failure. A change committed first prevents publication/retrieval only when the required operation-specific authority is lost. Native session invalidation denies stale proofs. After Manager designation withdrawal, fresh ordinary Receptionist authority retains permitted retrieval under its existing guards, and worker publication independently checks current recipient eligibility without requiring an active recipient session; publication/redemption committed first retains immutable evidence, but later reads/streams still reauthorize. Prove both orders with actual PostgreSQL blocker chains; verify effective F-01 paths and no new bypass during implementation. No scan/render/encryption/SMTP/push/client wait under domain locks.

All new durable command receipts bind normalized operation, URL target/artifact and typed body. Replay checks live authority, target visibility, digest and saved projection's target relationships before returning the original result. No raw token, mutable current data substituted for historical result, or fabricated historical receipt. Unknown DB commit requires independent matching receipt/row/generation readback before another mutation; definite rollback may retry under fresh signed proof. Stale attempts cannot complete/retry/dispose material.

## File Finalization and Cleanup

1. Short authorized transaction validates class/patient/Visit, policy and quotas, reserves server-owned attachment/staging generation and records no readable object.
2. Each bounded raw chunk uses its own signed upload request: the API and PostgreSQL independently hash its actual bytes; the reservation binds the upload identity, generation, position, length/digest and BFF whole-file length/digest. Stage immutable bytes outside locks, then use a separately signed typed publication request for that exact candidate and position; only the committed fenced CAS advances contiguous offset and accounts for its allocated quota once. A fresh signed status read reconciles unknown commit before further mutation. Public resubmission after BFF interruption revalidates the entire file identity, explicit current generation/revision, every committed prefix chunk and exact current offset via the existing signed status protocol in HTTP; unknown results block continuation, stale selectors conflict, and verified committed progress is never appended again. An identical committed same-offset replay acknowledges saved progress; identical bytes at another valid contiguous offset are a separate position; gaps, conflicts, overlap, stale generation or changed whole-file identity leave progress unchanged. Before final chunk publication independently measure/hash the assembled API file outside locks, binding its verified whole length/digest to the immutable candidate sequence and generation before STAGED; content detection, ClamAV scan and AES-GCM candidate write occur outside critical locks. Configured quota reservations prevent concurrent uploads exceeding policy; reservations are released only under fenced cleanup/finalization.
3. Short final transaction rechecks current actor/tenant/resource/class/policy and matching generation/source digest, then atomically publishes CLEAN metadata, object reference, audit and immutable success receipt. No success before encrypted bytes are durable and authenticated. Dependency failure leaves unreadable state, not partial successful disclosure.
4. Cleanup claims only a non-clean generation that is definitively abandoned/failed or whose configured ownership lease expired, with no active owner, no committed object reference and no unresolved transaction outcome. Reconcile unknown commit before eligibility; expiry alone does not prove rollback or permission to dispose. Under the shared authority/resource order and configured disposal eligibility, atomically compare generation/lease/state and claim/fence it as CLEANUP_CLAIMED. Missing/invalid policy, live lease, uncertain ownership/commit or committed CLEAN reference denies the claim. A claimed generation cannot finalize; retry uses a new eligible generation. Physical disposal occurs outside locks only for the immutable locator of that fenced generation; matching generation completes DISPOSED/releases quota. Stale cleaners cannot touch replacements, committed objects or retained clinical/history/audit evidence. Quarantine remains governed by its configured disposal policy; no implicit release or retention interval.

Prove same-tenant wrong-patient and foreign Visit FK failures, allowed preliminary null Visit, upload/read independence, policy limit boundaries, type spoof/EICAR/scanner outage/key/tag failures, and finalize-versus-cleanup both orders. Use generated opaque locators and no-follow root-bounded regular-file access; client names never choose a path.

## Export and Grant Transactions

Reserve one logical export by actual actor/tenant/operation/key/normalized patient/format/purpose/evidence digest, with fenced generation. Extract the full permitted record and manifest from one composed SQL statement snapshot under export-only scope. Render/neutralize/encrypt both artifacts privately outside critical locks. Reauthorize at finalization; READY artifacts, one success audit and safe receipt commit together. Interrupted generation leaves no READY partial record; reconciliation never creates a second logical export. Staging failure need not erase retained internal failure evidence.

B-22 reuses B-21's candidate cleanup handler and authority-first lock order for uncommitted export record/manifest candidates: reconcile the logical operation and both artifact references, verify configured disposal policy and no live owner/lease or committed reference, fence the exact abandoned generation, dispose only its immutable locators outside locks, and complete/release only matching-generation reservations. No disposal of a READY artifact or partial READY reference. B-22 proves both orders with real PostgreSQL checkpoints/blockers: READY publication first preserves both artifacts, audit/receipt and quota ownership against cleanup; cleanup claim first fences both candidates and prevents stale publication, with zero READY references/success audit/receipt and no replacement deletion or quota release. Aborted or interrupted publication may leave protected unreadable candidates until eligible cleanup; expiry alone never proves rollback. This reuses B-21 ownership and B-22's existing dependency, not another handler or Master edge.

Before disclosure issue a fresh digest-only grant for one artifact under live authority and positive handoff confirmation by actual acting staff for the same intended recipient/export. Creation verification is preparatory evidence only; record actual verifier, time, outcome and recipient linkage at grant issuance. Decrypt/authenticate to a protected temporary result outside locks. Immediately before serving use a short fresh authorized transaction to recheck readiness, class/session/security/tenant state, matching positive handoff evidence and unused/unexpired exact-target grant; atomically consume and audit, commit, then serve verified bytes. No unverified plaintext escapes. Concurrent second redemption loses CAS; interruption/lost response leaves grant consumed. Revocation committed before redemption denies; an already authorized/transmitted disclosure cannot be recalled. Test both ordered outcomes without keeping a transaction open through network delivery. Server redemption proves disclosure to the exporter only; actual onward handoff requires staff recipient verification at that time, not an inference from READY/download or a new legal verification method.

Record and manifest grants are independent. Grant issue/redemption does not change ordinary Patient/Visit/attachment field permissions. Audit records minimal purpose/recipient/verification/action/result, never full documents, bearer, ciphertext key or storage path. Export legal/disclosure policy remains OPEN-OPS-03.

## Notification Publication and Streaming

Originating owners commit domain/history/audit/outbox together. B-23 claims only committed events using tenant capability and `FOR UPDATE SKIP LOCKED`, commits durable generation/lease ownership, then validates source type/actual origin and safe payload. Current eligible recipients are checked before publication. Publication inserts unique recipient/type notifications plus delivery outcome in one transaction; tenant stream-state lock serializes position allocation through commit. An allocation rolled back is not an undisclosed gap; a later publication cannot overtake an uncommitted earlier position.

Claim/reclaim fences every completion/retry. Repeated dispatch/reconnect can replay the same notification but cannot create another logical event/recipient/type row or repeat cancellation/reschedule/admission. Companion ordinary/Doctor-specific source messages must map without duplicate review effects. Denied/revoked recipients receive no protected content; existing unread records confer no ongoing rights.

Definitive publication failure at the configured attempt bound atomically records terminal failed delivery for the matching active generation; no further automatic claims/retries and no recipient notification if none committed. Reconcile unknown publication outcome first and preserve any committed unique notification/success outcome. Retain source event and minimal safe failure category/existing attempt reference for authorized operational diagnostics through existing protected maintenance access and sanitized operational telemetry only; no new endpoint, role, table SELECT grant, patient details or clinic-visible failure notice. No business rollback or fabricated notification; current authorized snapshot remains the recovery path.

BFF streams via fresh signed private batches, translating public reconnect cursor and bounded batch/projection selectors into the canonical signed query, never trusting an unsigned forwarded cursor header. Reject duplicate/conflicting cursor forms. Release DB transactions before network waits, recheck live session on subscribe/periodically/before send, and discard buffered payload on access loss. API filters each read by current role/recipient/tenant. Snapshot rows and publication watermark share one statement snapshot. Integrity-protect the derived cursor's organization, recipient, stream/projection version and committed position; validate every binding against the current authorized recipient and projection, reject tampering/mismatch and explicitly signal unavailable history. Cursor supplies no authorization and needs no new persistence. No timestamp/UUID/naive global-sequence cursor or cross-tenant replay.

SSE `sse_poll_interval_ms`, `sse_batch_limit` and `sse_max_auth_recheck_interval_ms` policies must be explicitly configured, including idle rechecks. Bind the canonical effective `policy_digest` in the signed private stream query per HTTP; mismatched effective policy, missing/invalid values or unavailable/failed authorization checks refuse or terminate the stream, discard buffered data and prevent further protected frames. Recheck each read and immediately before protected emission irrespective of the periodic bound; never use the interval as a cached permission lifetime.
