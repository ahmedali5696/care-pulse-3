# HTTP Contracts: Wave 4 Supporting Services

**Status**: Planned technical contracts under [plan.md](../plan.md); no routes are implemented by this document. Binding operation families come from implementation-plan §11.1. [Data model](../data-model.md) and [transactions](transactions.md) define persistence/recovery.

## Shared Boundary and Results

Paths below use the approved logical path. Public Next.js routes use `/api` plus that path; normal private API routes use `/v1` plus that path. Dedicated stream and binary/download translations are specified below. No direct browser-to-private-API route is exposed.

- BFF verifies real Better Auth session and live authorization; unsafe methods require existing strict Origin/CSRF controls. Strip untrusted identity headers, derive actual actor/tenant and sign canonical method/path/query/exact body digest/identity/time/new nonce. API independently verifies F-01 proof and live operation/resource authority. No browser-supplied actor/role/tenant/scan/encryption state is accepted.
- Extra-forbid typed command DTOs, configured bounded strings/pages/date ranges/binary lengths, safe UUID/date parsing, decimal-string money and role-specific projection. Foreign and missing resources return the same 404; unauthorized known operation returns 403 without content.
- JSON success retains existing `{data, revision, event_id?}` with 200/201 and `Cache-Control: no-store`. Error retains `{error:{code,message,request_id}}`; no raw SQL, filesystem path, scanner content, key or PHI. Binary/SSE successes use their declared content type, not a JSON envelope.
- Preserve existing statuses/codes: 401 UNAUTHENTICATED, 403 FORBIDDEN, 404 NOT_FOUND, 409 CONFLICT/IDEMPOTENCY_CONFLICT/STALE_REVISION where applicable, 422 INVALID_INPUT, 429 RATE_LIMITED, 503 UNAVAILABLE. Invalid class/type/size or unknown fields use sanitized 422; unavailable scanner/key/storage uses 503 with no success. Non-ready/reused/expired grants disclose no content; do not invent an existence-revealing result.
- Logical creation/finalization/subscription commands use existing `Idempotency-Key`/expected revision conventions. Digest binds operation, normalized URL resource and typed body, including artifact/query selectors. Fresh signed nonce per request, including retries. Same authorized operation/key/target/body returns immutable committed safe projection; changed target/body conflicts after visibility checks. Revoke/disable checks precede receipt replay. Never save raw grants or private paths in receipts.
- Grant issuance is fresh security-material issuance with no raw-token receipt replay. Lost grant response requires a newly authorized issuance. Export creation replay returns export/artifact identity, not a renewed grant.
- Require valid explicit operation configuration before serving: missing/invalid grant lifetime, file class/type/size/count/quota, storage/key/scanner, retry/lease/cleanup policy, SSE poll/batch/recheck bounds or push transport policy disables the affected operation (sanitized 503 UNAVAILABLE), or fails readiness/startup when required by F-03. No unlimited defaults; no grant issuance/redemption, unsafe publication, unconfigured retry/disposal or stream/push bypass. An active SSE stream closes on invalid configuration/recheck failure. Labeled synthetic values do not approve production.

### BFF policy boundary

Extend the existing server-only, protected `CP_POLICY_FILE` loaders in Web and API together. Preserve exact-key validation, duplicate-key rejection, protected regular-file access and approved profile checks. Reuse the existing `file_policy` fields (`allowed_extensions`, `allowed_mime_types`, `allowed_classes`, `max_file_bytes`, `max_files_per_record`, `max_total_storage_bytes_per_record`, `scanner_required`, `quarantine_on_failure`) and `download_grant_expiry_seconds`; add explicit top-level positive bounded integer fields `sse_poll_interval_ms`, `sse_batch_limit` and `sse_max_auth_recheck_interval_ms`. No environment fallback, browser configuration or default values. API remains authoritative for record counts, cumulative quota, actual content detection and scan/publication; the BFF independently enforces the file envelope and its own bounded spooling, and never accepts a scan bypass. For enabled medical attachment processing, `scanner_required=false` is invalid in either Web or API, even if both policies agree. Fail closed before upload body consumption/spooling, reservation or processing with sanitized 503 UNAVAILABLE, or fail required readiness/startup under F-03. Definitive complete clean scan evidence bound to the immutable source digest is mandatory before CLEAN publication. This validation is specific to enabled medical attachment processing and does not change unrelated baseline capabilities.

Before reading/spooling upload bytes or opening an SSE response/allocating its poll loop, BFF must validate its current local policy and obtain a fresh authorized private response confirming agreement with the API's independently loaded policy. Use a signed query `policy_digest` on all listed private attachment/export phases (including metadata, status, grant issue, preflight and redeem) and private event stream/snapshot reads: lowercase SHA-256 of UTF-8 compact JSON of the relevant validated policy subset (file: profile, file_policy and download_grant_expiry_seconds; SSE: profile and the three SSE fields), keys sorted lexicographically at each object level, allowlist arrays sorted lexicographically, JSON booleans and decimal integers, no whitespace. API recomputes it, rejects missing/invalid/mismatched values with sanitized 503 before effects or payload, and rechecks at every relevant phase/read. Initial upload status and first bounded stream read are the respective pre-resource checks. Reject inconsistent configuration even if the stricter value might allow the request; BFF must not downgrade to generic forwarding. On change/failure during processing, cease forwarding/emission, discard protected buffers/spool safely, and reconcile any previously committed fenced progress. No policy document or digest becomes a client authority.

### Dedicated Binary Adapter

The current BFF, API `_read_body` and inherited PostgreSQL `f01_register_proof` each retain the existing **1,048,576-byte (1 MiB) per-request body ceiling**. This is a transport/proof-registration bound, not a production file-size policy. Keep all existing JSON limits unchanged and retain the database's independent hashing of actual body bytes; do not submit only metadata or a caller-supplied digest in place of binary proof bytes.

BFF rejects missing, duplicate, unknown or invalid public upload query selectors before reading the body. It signs the supplied `generation` in the private status precheck and compares the returned authorized generation/revision with the supplied `generation`/`expected_revision`; mismatch conflicts before spooling. The first chunk of a new upload signs the supplied revision; a resumed upload uses the explicitly supplied and freshly verified current revision at the verified committed offset as specified below. Later chunks sign only the current revision established by the matching committed acknowledgment or its reconciled status in the same generation. BFF privately spools the complete policy-bounded public upload after the authorized policy/status check, measures/hashes the actual bytes, then forwards it through **contiguous raw binary chunks**, using consecutive 1 MiB chunks except the final remainder, using repeated private `POST /v1/attachments/{id}/upload` calls. Each chunk has a fresh current-session check, signed nonce/timestamp, independent proof registration/PRIMARY binding and canonical signed query containing `generation`, `offset`, `total_length`, `whole_digest`, `expected_revision` and `policy_digest`. API independently hashes each received chunk; PostgreSQL receives those exact chunk bytes and independently compares their SHA-256 with the signed envelope. Digests are lowercase 64-character SHA-256 hex; offsets/lengths are nonnegative bounded integers, chunk lengths positive, and generation/revision are current bounded counters. Query/envelope bounds and strict duplicate/unknown-parameter rejection remain binding. Do not base64-wrap or multipart-wrap a maximum-size chunk and exceed the body limit.

The binary call reserves an immutable server-generated `StagingAttempt.attempt_id` UUID, tenant-qualified and bound to the operation, owner, phase and generation, and the exact next chunk identity (generation, offset, actual length/digest, total length/whole digest, revision and current claimant/lease) under its PRIMARY and stages immutable candidate bytes outside critical locks. A successful staging response is returned only after the immutable candidate is durable and verified: `attempt_id`, `generation`, `offset`, `chunk_length`, `chunk_digest`, `total_length`, `whole_digest`, and current post-reservation `revision`. It is not a committed append acknowledgment. A separate fresh signed `POST /v1/attachments/{id}/upload/publish` accepts an extra-forbid typed JSON body with `attempt_id`, `generation`, `offset`, `chunk_length`, `chunk_digest`, `total_length`, `whole_digest` and `expected_revision` (the returned current post-reservation revision); `policy_digest` is in the signed query. IDs are strict UUIDs, counters/lengths bounded integers and digests lowercase SHA-256 hex. Under the current fenced owner and authorization it commits the candidate metadata and contiguous offset, returning `attempt_id`, `generation`, `offset`, `chunk_length`, `chunk_digest`, `committed_offset`, `revision` and `state` under the existing success envelope. A matching completed replay returns the saved acknowledgment after fresh authorization; stale/conflicting phase or identity denies with sanitized conflict, malformed selectors with invalid input, and unavailable verification with unavailable. No raw bytes are re-signed as metadata in lieu of the original binary proof; publication must match the recorded actual proof digest and immutable candidate. No second PRIMARY on the original proof.

Accept only the next contiguous offset; reject gaps, overlap, changed total/digest, wrong generation and conflicting bytes. Identical already committed chunk replay under fresh proof returns its saved acknowledgment without appending twice. Before the last chunk can publish STAGED, independently measure/hash the assembled API file outside critical locks and bind that verified assembly result to the exact immutable candidate sequence, full length/digest and generation in publication. Incomplete/mismatched assembly never becomes STAGED. Scan and content/type checks apply to the assembled file, not isolated chunks.

`GET /v1/attachments/{id}/upload/status` accepts strict signed query `generation`, `policy_digest` and optionally the complete identity (`offset`, `chunk_length`, `chunk_digest`, `total_length`, `whole_digest`), never a partial identity. Return only current authorized `generation`, `revision`, `state`, `committed_offset` and, for an exact identity, the matching `attempt_id`, phase/outcome and saved committed acknowledgment if present, without paths or bytes. A lost stage/publication response requires status readback before retry; an exact committed chunk returns acknowledgment; a committed reservation with independently verified durable matching candidate permits only its fresh publication; status must not infer candidate durability from reservation commit alone. Pending/unknown outcome or live incomplete staging blocks competing append. A definitively failed or aborted stage is reconciled under the existing generation/lease rules before any restage, and definite non-commit permits only the current eligible phase under fresh proof. Status itself is read-only; any needed candidate-byte verification occurs outside critical locks and publication revalidates the immutable candidate/fence. No arbitrary pending-to-success promotion. Expired or cleanup-owned attempts are fenced; resume/reprepare only under current authorized generation after reconciliation. Never treat a stale offset, digest or receipt as authority. After BFF interruption, the client resubmits the complete file with explicitly current generation and expected_revision (obtain current selectors through the existing authorized metadata read); stale selectors conflict rather than being silently replaced. Repeat the authorized pre-spool policy/status check, spool and independently measure the entire resubmitted body, then freshly recheck generation/revision/committed_offset and the complete file length/digest against any pinned upload identity, including an uncommitted reservation. Use the same deterministic chunk partition (consecutive 1 MiB chunks except the final remainder), and fresh signed exact-identity status reads for every chunk in the committed prefix: verify each offset, length, digest, matching attempt identity and committed acknowledgment, and confirm that the verified contiguous prefix ends exactly at the current committed_offset. An exact-identity status read must reject conflicting pinned whole-file identity or conflicting occupied chunk identity, not treat it as absent. Reconcile any pending or unknown stage/publication at the next offset through that same status protocol before further mutation; unresolved status blocks continuation. Resume only at the verified current offset using the current checked revision, advancing it only through verified matching stage/publication acknowledgments or their reconciled status outcomes; unexpected generation/revision/offset changes conflict and require an explicit fresh authorized retry. Never skip unverified chunks, duplicate progress/quota, silently override stale selectors or infer non-commit from a lost response. If the whole file is already committed and verified, return the matching safe upload result without appending.

Enforce configured total-file/type/class/count/storage limits and quota reservations at initiation, cumulative upload, assembly and publication; chunking cannot bypass them. Reject extra/missing/truncated bytes, dishonest Content-Length and per-chunk overflow (including streamed bodies without Content-Length) before success. A policy-permitted file larger than 1 MiB is transportable through multiple bounded proofs; no new production file maximum or security duration is selected. Missing required policy fails closed. Web uses protected ephemeral storage and gains no access to retained `private_files`; interruption/expiry preserves only non-readable fenced progress for authorized reconciliation or cleanup.

Public downloads remain GET. BFF reads `X-Download-Grant`, then makes fresh signed private **POST** calls to `/v1/attachments/{id}/download/preflight` and `/download/redeem` (or the exact `/v1/exports/{id}` subroutes below), with typed JSON containing bearer and, for exports, artifact selector. Preflight prepares authenticated decryption without consuming the grant and returns an opaque preflight attempt ID; redeem also binds that ID and gets its own newly authorized proof, returning verified binary bytes only after atomic consumption. This translation binds the bearer to each signed body without putting it in a URL or pretending an unsigned custom header is authenticated. Register each private method/purpose/target explicitly in API and F-01. Do not log these bodies. BFF passes safe content headers only; disconnect or lost response never restores consumed authority. Read-only download status accepts the opaque attempt ID (and export artifact selector) in the signed query; it returns only matching safe committed/aborted/pending outcome to the original authorized actor/session, never a bearer or bytes. A lost preflight response before redemption may use a fresh authorized preflight; it cannot make an already consumed grant usable.

Finalization/export creation/download are orchestrations of the separately signed private phases defined by the transaction lifecycle and exact inventory below. Finalize prepare binds the logical idempotency key/digest, current staged generation and revision; publish binds the returned attempt ID, same logical command identity, expected revision, generation and verified candidate/source digest. Status binds the logical key/digest and generation, and reads only safe phase/receipt state. Export reserve creates or returns the same logical export identity for its patient/key/digest, extract binds that export/generation and returns the one authorized snapshot for private rendering, and publish binds the same operation/generation, extraction identity and both immutable artifact digests. Export status is patient-scoped so reserve can be reconciled even when its response/ID was lost. All publication evidence is server-produced and checked against persisted work, never trusted browser fields. These phases never reopen a registered PRIMARY. Sign publication/redemption only after external work and fresh authentication; on expiry, revocation or unknown commit reconcile as specified there. The 1 MiB bound is for request bodies, not an invented response/file cap; bounded authorized binary responses still require full GCM validation before disclosure.

### Stream Adapter and Recovery

BFF SSE uses a dedicated adapter, not generic `forwardPrivate`. For each configured bounded poll it obtains a fresh signed private read at `/v1/events/stream` returning JSON `{items,cursor,requires_snapshot}`; this private route is a bounded batch, not an indefinitely authorized stream. Validate matching policy and authorization on the first bounded private read before opening the public SSE response. Every request gets a new nonce/F-01 transaction. BFF checks current session on subscribe, at configured periodic intervals and before emitting protected data; API checks live actor/tenant/resource/fields for each read. Stop/drop buffered protected data on invalidation or disconnect. Never hold DB locks while waiting on the client. Each eligible item carries its own integrity-protected continuation cursor for that committed position, bound to the recipient, tenant and projection. Use that cursor as the corresponding public frame ID. The batch cursor is for the next private poll after processing the batch. Never send it on an earlier frame or advance the public ID for filtered items or keepalives. On disconnect, resume from the last observed frame ID with live filtering, stable-identity deduplication and the existing snapshot fallback.

Required named configuration policies: SSE poll interval, batch bound and maximum authorization-recheck interval (including idle connections). No numeric values are selected. Subscribe and every read/emission require live checks; the elapsed time between periodic rechecks cannot exceed the configured maximum, including during slow-client backpressure. Client write/drain waits must not suspend authorization checks; if live reauthorization cannot be established within that maximum, terminate independently of client progress, cancel pending writes and dispose of unsent protected buffers. Already transmitted bytes cannot be recalled. Missing/invalid policy, unavailable/failed recheck or loss of access refuses the stream or closes it immediately upon detection and drops buffered protected data; no protected frame after a failed check. Push uses its own immediate pre-send authorization/consent check, not the SSE interval.

BFF normalizes the public reconnect cursor into the private canonical signed query (`cursor`, bounded `limit`, allowed projection selectors and `policy_digest`). API consumes only that signed query, never an unsigned forwarded `Last-Event-ID` header. Reject duplicate parameters and conflicting header/query cursor forms; bind selectors to the same F-01 request/resource scope. Each next poll signs its newly returned cursor afresh.

`GET /events/snapshot` returns current authorized operational snapshot, `stream_projection_version` and matching cursor/watermark from one statement snapshot. If replay history is unavailable or incompatible, send a non-sensitive recovery signal and require snapshot/refetch; never silently skip a gap or expose another recipient's event. No invented replay retention/heartbeat/security duration.

Both require live Doctor authority and Origin/CSRF; Receptionist/Manager/operator denied. Same-body authorized replay has no duplicate subscription effect and cannot resurrect revoked consent.

Validate subscription key/endpoint shape and prevent requests to internal/loopback/private targets or redirect bypass. At registration and send validate DNS-resolved destinations against the permitted address policy; at transport bind each connection to a validated permitted numeric address before connecting and verify the actual connected peer matches it before sending any payload. No uncontrolled DNS re-resolution or fallback may substitute another address. Repeat the validation and binding for every reconnect and any followed redirect, or reject it; disable implicit/environment proxy routing and reject proxy paths that cannot enforce the same actual-destination binding. Preserve TLS SNI and hostname/certificate verification against the intended HTTPS hostname, not the pinned IP as a substitute. Fail closed when binding or verification cannot be guaranteed. Transport endpoint material stays protected and excluded from ordinary responses/logs. Recheck Doctor/session/tenant/device consent and current name-consent immediately before sending; logout/reset/disable/suspension/withdrawal suppress later sends. Provider-expired subscriptions become inactive. ## Metric Dictionary and Reports — B-26

`GET /metrics/dictionary` returns versioned IDs, units, populations/statuses, service/event date basis, replacement handling and applicable numerator/denominator/empty-population definitions. `GET /dashboard?service_date=YYYY-MM-DD` returns named status/value counters, dictionary version, Cairo date and `as_of`. `GET /reports/trends` accepts bounded date range, named base metric and day/week/month bucket; `GET /reports/throughput` accepts bounded event-time range/bucket and explicitly identifies admission count. All are current tenant staff aggregate-only projections under narrow F-01 read scopes. Both report queries require exactly one of each listed key. Trends requires `start_date` and `end_date` (valid ASCII YYYY-MM-DD Cairo dates), `metric` (exact supported dictionary base measure, excluding the trend wrapper) and `bucket` (`day`, `week` or `month`). Select [start_date,end_date) by service_date for service measures or Cairo-local event date for event measures, then group selected rows by the approved calendar buckets. For start_date=2026-11-21 and end_date=2026-11-28, Friday the 27th is included and Saturday the 28th excluded. Throughput requires `start_at`, `end_at` (valid UTC instants in exact YYYY-MM-DDTHH:MM:SSZ form) and `bucket=day`. Count distinct admissions with start_at <= admitted_at < end_at and label buckets by Cairo event date. For 2026-11-27T22:00:00Z through 2026-11-28T22:00:00Z an admission exactly at the first instant counts; one exactly at the second belongs to the next interval. In both routes reject empty/reversed/excessive ranges, missing/extra/duplicate keys, invalid dates, unsupported enum values and noncanonical scalar spellings. BFF validates then signs the exact canonical query using the existing query encoder; API and F-01 independently validate the same bound selectors and purpose. Enforce the applicable existing range limit; if none applies, require an explicitly validated positive maximum span in calendar days for trends and elapsed seconds for throughput. Missing/invalid bound disables the affected route. No production value is selected.
