# Wave 1 Internal Security and Lifecycle Contracts

Owners: D-01/D-02/D-09 and B-01–04. Preserve master §§2/11.1 and [spec SEC-01–06/RACE-01–09](../spec.md). Concrete encodings below are design choices within that approved protocol; no new service or production policy is selected.

## 1. Signed BFF → FastAPI envelope

The BFF accepts only approved same-origin routes and methods, checks the actual Better Auth session and live authority, strips browser `X-CarePulse-*` headers, and constructs fresh identity. It forwards no Cookie/Authorization bearer credential to FastAPI. A service credential alone never authenticates a staff operation.

The signed envelope carries: protocol version, signing key ID, service identity, method, normalized received path, canonical query, exact body SHA-256, tenant ID, actor/staff ID, non-bearer native session ID, role, captured security revision, timestamp, nonce, operation purpose and idempotency key (empty when absent). Bootstrap/recovery integration uses an explicit purpose and validated proof-bound auth identity rather than pretending to have an ACTIVE staff session. Each purpose has an exact command allowlist; recovery integration grants no clinical access.

**Canonical representation**: a fixed-order JSON array of strings, compact UTF-8 with no optional whitespace, signed using HMAC-SHA256. Field order is the order listed above. Both implementations must share golden vectors. Include the key ID/purpose/idempotency key in signed bytes; never concatenate unescaped user strings with ambiguous delimiters.

- Uppercase HTTP method. Hash the actual forwarded byte body, including empty bytes; do not reserialize JSON after signing. JSON business normalization is separate and used only for idempotency.
- Accept valid UTF-8 paths; reject malformed escapes, ambiguous encoded separators, dot-segment/backslash traversal or a normalization that selects another route. Normalize and forward the same path that is signed; API recomputes from what it receives.
- Parse query pairs preserving duplicates, normalize RFC3986 percent encoding and deterministically sort by encoded name then encoded value. Reject duplicate singleton parameters at route validation; do not collapse duplicates before authentication.
- Emit identity headers once from a fixed allowlist. API inspects raw headers and rejects missing/duplicate identity/signature/key/time/nonce fields, unknown key IDs, malformed values, invalid constant-time signature comparison or body/method/path/query mismatch.
- Timestamp is canonical UTC epoch milliseconds; fixture-configured freshness/skew controls acceptance. Reject age at/after freshness limit and future offset beyond allowed skew. No implicit duration. Nonce must be nonempty high-entropy single-use request material generated server-side.

Only after service/key/signature/freshness verification insert `(key_id, nonce)` durably in the protected nonce store. A conflicting insert denies the request. This short anti-replay transaction is separate from business work: domain rollback does not make the envelope reusable. Purge only after the authenticated timestamp can no longer fall in any configured accepted window. Signature failures never authorize a tenant context.

## 2. Live operation boundary and idempotency

For ordinary protected requests, start tenant transaction with validated UUID context; lock tenant/live-permission state and check ACTIVE, actual session still present/usable, current staff enabled/verified/role/grants, captured security revision and session deadlines. Signed identity is necessary but not sufficient. Do not simply compare the signature's role to a route role and skip current DB state.

Sensitive commands and revocations serialize on the same authorization barrier. If a protected command wins first it commits before revocation; if revocation wins, the old command fails. No request using withdrawn authority can commit sensitive work after the revocation commit. Read projections use current authorization and never expand forbidden nested content.

Only then evaluate role/resource/field access and shared idempotency receipt. Receipt lookup is tenant+actor+operation+key scoped. Normalize typed request semantics deterministically, preserving meaningful values; changed body conflicts. Concurrent identical requests commit one result. Receipt, successful domain mutation, audit and outbox/jobs share the domain transaction. A fresh nonce is required on every retry, including a cached-result request. Revoked callers receive no cached protected result.

Retain transaction cleanup under success, rollback, SQL error and cancellation; prove actual pooled connection reuse. A narrow verified Owner-activation command is the sole PROVISIONING clinic exception, not a general session or patient/settings operation.

## 3. Session policy overlay on supported Better Auth sessions

Use supported server-owned additional session fields (input disabled) for immutable absolute deadline, last validated activity and captured security revision. Native Better Auth session ID/token remains the only authenticated session. No standalone session engine or cookie cache.

- Before verifying login credentials capture the current permitted staff/security revision. Bind the created session only if that same revision remains valid; never stamp a newer revision after an old password was checked. A raced session is revoked/unusable and no successful cookie is returned.
- Session is usable only while native Better Auth validation succeeds, `now < absolute_deadline`, and `now < last_activity + configured_idle_timeout`. Equality expires. Do not renew any native session past absolute deadline. Neither `freshAge` nor sliding `expiresIn` substitutes for this policy.
- Update activity conditionally on a still-valid session and revision; concurrent stale activity cannot revive an expired/deleted session or roll activity backward. The BFF and API must agree on boundary behavior and revalidate on each protected operation. Refresh propagates legitimate Set-Cookie only to the browser, never to FastAPI.
- Enforce Origin/CSRF and configured identity/source throttles explicitly in custom server wrappers: calling `auth.api` directly is not proof those HTTP controls ran. Password/login/reset output is sanitized; no bearer token returned in JSON.
- Disable/grant withdrawal commits revision/state first, then removes associated auth sessions. Cleanup failure leaves old revisions unusable in both boundaries. Re-enable cannot revive old sessions. Tenant suspension blocks immediately; preserve data.

All policy values come from explicit labeled synthetic configuration now. Production must retain fail-closed policy gating. No chosen value, default password-policy change, rate window or lifetime is authorized by this contract.

## 4. Invitation issue and acceptance

Issue random single-use proof, store digest verification and separately protected delivery material; commit invitation, actor/reason audit and nonclinical job together. Reissue atomically revokes/supersedes the old proof. Do not send SMTP inside the transaction.

Prepare Better Auth identity outside critical domain locks; it remains unusable. Verify intended email/proof binding, then send only the signed purpose-bound activation command. Under Organization then invitation locks: recheck current state, expiry (`now < expires_at`), nonconsumption/nonrevocation, prepared verified identity, unique Owner invariant and expected revision. Atomically consume invitation, establish enabled Owner association, record audit and change PROVISIONING to ACTIVE.

Concurrent acceptance can produce only one Owner. Failed preparation/finalization leaves no usable partial identity; safe retry may reconcile the same preparation. Revoke/reissue/suspend races serialize; a SUSPENDED clinic never activates via acceptance. Ordinary operations before ACTIVE always fail. Receptionist invitation acceptance similarly rechecks current ACTIVE clinic, target identity/role and invitation; it cannot activate an Owner or restore withdrawn authority accidentally.

## 5. Recovery issuance and durable reset coordination

### Issue

Public reset request is non-enumerating and configured-rate-limited. Only a currently eligible verified registered Owner identity receives recovery proof. A reset-owned block alone does not prevent issuing fresh recovery proof to an otherwise eligible Owner: this permits recovery from an expired abandoned attempt, without bypassing any live disablement/suspension restriction or clearing the block on issuance. In a supported Better Auth transaction context, create digest-stored verification and D-09's mapped nonclinical delivery intent together. Required audit metadata in that unit contains no proof or password. The extension's issuance callback persists intent only, without background/SMTP work. A failure after either write rolls back both; verify this against the actual adapter.

### Operation identity and reservation (U1)

Cross-process operations are not one Python transaction. A server-generated immutable `operation_id` is bound to one `(purpose, proof_digest)` by a durable unique constraint, retained after consumption. A partial unique constraint on native `auth_user_id` where `closed_at IS NULL` allows only one unresolved reset per credential identity, even if two different valid proofs exist. The staff block stores `reset_block_operation_id`, not an unowned boolean. Store captured tenant lifecycle and staff/security revisions, state, invalidation flag and auth fence on the operation. `RESERVED` → `AUTH_DONE` → `FINALIZED` is the success path; reconciled failure may close as `ABORTED`; a revocation-invalidated `AUTH_DONE` may also close `ABORTED` only through the evidence-fenced distinct-proof recovery branch below, retaining its immutable completion. Completion evidence is unique per operation; successful reset audit is unique per operation/action.

Validate the submitted credential through the supported existing password policy before reservation; do not invent another policy. Bind the exact desired credential to this operation using a server-computed HMAC-SHA256 request fingerprint over an unambiguous versioned encoding of purpose, tenant/staff/native-user IDs, proof digest and the exact submitted password bytes. Do not trim/normalize passwords. Use a purpose-separated key derived from the externally held BFF auth secret, record its key version and retain required versions for the supported retry lifecycle. Persist no password, raw proof or unkeyed password digest; a plain hash would enable offline guessing. The signed recovery-purpose request covers the fingerprint; the browser cannot supply a trusted fingerprint or choose another identity. Missing required key version fails closed.

Under Organization → Staff/live-authority → RecoveryOperation locks:

1. Resolve an existing operation by proof digest before treating a consumed verification row as an unknown proof. Compare its request fingerprint in constant time and recheck recovery-purpose binding. Coordination may pass its own reset block only, never another block or live restriction. A matching retry reuses its operation and reserved revision; a different password is `409 IDEMPOTENCY_CONFLICT`, including after completion. Neither case increments revision or replaces the block again; `ABORTED` cannot restart with that proof.
2. For a new operation, revalidate the actual supported verification row's identity/purpose/binding, current Owner eligibility and strict `db_now < expires_at` inside the reservation transaction before any block. Random/expired/revoked/mismatched proof cannot block an account. Sample database time after acquiring the locks. A different proof for an identity with an unresolved *eligible* operation gets sanitized `409 RESET_IN_PROGRESS`; do not consume either proof, create a second operation or change the winner's revision/block. An expired, incomplete predecessor or a separately revocation-invalidated `AUTH_DONE` predecessor may undergo only its matching evidence-fenced reconciliation branch below, without clearing the reset block. Unique constraints backstop the checks.
3. Insert the operation, increment security revision **once**, capture the resulting security revision and current lifecycle/staff revisions, and set its owned authorization block in the same commit. Record pending security evidence, not successful reset audit. Old sessions now fail. Release all domain locks before calling auth. A lost reservation response is resolved by the proof binding, not by creating a fresh operation.

### Durable auth effect and fencing

Use one outer **supported adapter transaction** for the mapped operation fence, native reset and mapped completion evidence. Native transaction nesting must reuse that adapter/connection. Do not infer cross-process safety from a JavaScript mutex or from a transaction wrapper alone.

1. Acquire a real row-write lock with a guarded atomic fence increment on the operation, requiring operation ID, matching fingerprint, `state=RESERVED` and `invalidated=false`. Recheck after waiting. A competing handler waits, then either sees `AUTH_DONE` and uses its evidence or is denied; it must not run a second password change. An `AUTH_RUNNING` marker is transaction-local in effect: it rolls back to `RESERVED` on failure. No reset lease or timeout takeover is necessary.
2. While holding only that operation/auth lock, recheck proof binding and strict expiry, then call the supported native reset with database verification/session storage and `revokeSessionsOnPasswordReset=true`. Native proof consumption must be an atomic single-winner DB operation. Consume proof, change credential and delete existing sessions in this same transaction. The wrapper exposes no direct native-reset bypass; all handler errors propagate as rollback, not a swallowed error response.
3. Recheck strict expiry before recording completion; reaching expiry during processing rolls the entire transaction back. Persist immutable nonsecret completion evidence binding operation/proof/native-user IDs, request fingerprint, reserved revision, auth fence and completion time, then set `AUTH_DONE`. Commit all auth effects and evidence together. No SMTP, Python HTTP or other external process call occurs inside this transaction. Auth never acquires Organization/Staff locks after its operation lock.

Disablement, grant withdrawal and tenant suspension use their normal domain barrier and also mark applicable unresolved operations invalidated under their operation locks, in deterministic ID order. If revocation wins that lock, auth fencing fails; if auth wins, it finishes first and the later revocation prevents stale finalization. This does not move domain business rules into the BFF; its adapter extension only enforces the reserved nonclinical operation gate.

### Finalization and retry outcomes

Finalize under Organization → Staff → RecoveryOperation locks. Require non-invalidated durable completion with exact operation/proof/user/fingerprint/fence bindings, the operation's reserved security revision, unchanged relevant staff/lifecycle revisions, `invalidated=false` and `reset_block_operation_id=operation_id`. Close as `FINALIZED`, clear **only** this reset-owned block and append the single successful-reset audit atomically. Never set enabled/verified/grants/tenant state, decrement revisions, revive sessions or clear another operation's restriction. Return a minimal reset acknowledgment only after this commit; do not create a session. A concurrent finalizer observes `FINALIZED` and returns the same acknowledgment without another write/audit, subject to current recovery-purpose eligibility; it grants no current clinic access.

| Competing request / failure | Required durable outcome |
| --- | --- |
| Same proof + same password, before auth finishes | Same operation/revision; serialize on its fence and resume/wait, never replace it. |
| Same proof + different password | 409 conflict with no credential/block/revision change, even if the first request finished. |
| Two distinct valid proofs for one auth user | One unresolved reservation wins; the other gets 409 without proof consumption or extra blocking, except for the explicitly proved expired-incomplete or revocation-invalidated AUTH_DONE replacement branches below. A distinct still-valid proof can start a later operation only after the first closes and current eligibility is rechecked. |
| Crash before reservation commit | No reservation, block or revision change; normal valid retry. |
| Crash after reservation / auth rollback | Block remains, operation stays `RESERVED`, no completion or partial auth effects. A matching valid resubmission may retry auth; timeout alone proves nothing. |
| Crash after auth commit / lost auth response | `AUTH_DONE` and completion prove the auth effect; skip native reset, then finalize only if still non-invalidated and currently eligible. A later revocation-invalidated completion follows the distinct-proof branch. Never infer success merely because proof disappeared. |
| Finalization rollback / lost final response | Retry completion-based finalization or read the already finalized result; one success audit and no repeated credential effect. |
| Proof expired with no durable auth completion | No new consumption or success. Keep blocked pending reconciliation; never silently extend proof validity. |
| Proof expires after durable auth completion | Only non-invalidated AUTH_DONE finalization may use matching completion evidence after expiry: it consumes nothing and never changes a password again. |
| Disable/grant/lifecycle revision or block owner changed | Old finalizer affects nothing, keeps restrictions and reports sanitized conflict/unavailable, not success. An invalidated `AUTH_DONE` never passes completion-only finalization. No overwrite of newer authority. |

**Existing invocation contract (abandonment/reconciliation)**: A real user can request a fresh proof via existing non-enumerating `POST /api/auth/reset-request` even while blocked by their own incomplete or revocation-invalidated reset. Submitting that distinct, valid proof and desired password via existing same-origin, CSRF-guarded `POST /api/auth/reset-complete` makes the BFF validate the supported proof binding and current recovery-purpose eligibility, then call the already allowlisted signed, purpose-limited private recovery coordination in B-04/T051–T053 (not a public administration or new HTTP endpoint). The signed request uses server-derived user/proof identity and operation purpose; client-supplied IDs cannot choose the blocked identity or authorize closing another operation. For the expired-incomplete branch only, before reserving the new operation, under Organization → Staff → prior RecoveryOperation locks with the normal live-authority barrier, sample database time and check that the prior proof has **strictly expired**, no durable `AUTH_DONE`/completion evidence exists and no competing auth effect is still in progress. Locking the same auth-fence/operation row waits for any live adapter transaction; after waiting, re-evaluate all state and evidence. If still expired and incomplete, conditionally mark the old operation invalidated and `ABORTED` (retaining its proof binding/security evidence, without success audit), then atomically reserve the new validated proof and replace reset-block ownership, with **no unblocked interval** or unnecessary second reservation. Old handlers/finalizers are fenced out. A different proof while the prior operation is unexpired or uncertain is still `409 RESET_IN_PROGRESS`, without any mutation; missing/unverifiable evidence or concurrent lock failure fails closed. If prior `AUTH_DONE` exists without invalidation, use completion-only finalization, including after its proof expiry. A revocation-invalidated `AUTH_DONE` may be replaced only by the separate branch below; never use expiry or a merely changed revision to abandon a completed effect. An original-proof retry before replacement follows the original idempotent path; once A is `ABORTED`, all original-proof retries are denied and cannot restart or acknowledge it. An invalid/expired replacement proof cannot close the predecessor or clear its block.

**Revocation-invalidated `AUTH_DONE` replacement (U1):** This branch requires a distinct, currently valid purpose-/identity-bound proof B obtained through the same `reset-request`/`reset-complete` routes, and a currently verified enabled Doctor/Owner in an `ACTIVE` clinic after any reactivation. The coordinator derives the identity from B, not a client-selected A ID; independently checks B's proof/strict expiry and current Owner/clinic eligibility under the live-authority barrier, allowing only the existing reset-owned block. Reactivation alone neither unblocks nor finalizes A.

Under **Organization → Staff → RecoveryOperation** locks (operation rows in deterministic ID order when multiple apply), take a write lock on the same operation row guarded by auth's fence (without incrementing A's fence or re-running native reset), wait for a concurrent adapter transaction, then recheck with fresh DB time: A remains the reset-block owner and `AUTH_DONE`; its exact immutable completion matches operation/proof/native-user/fingerprint/reserved revision/fence/time; durable, transaction-linked authorization-revocation evidence explicitly invalidated A (including the affected operation and committed authority revision, never inferred from timeout or incidental revision change); the captured-vs-current authority and revocation sequence are consistent; and proof B remains distinct, unconsumed, valid and linked to this same eligible Owner. Recheck no newer suspension/disable/grant withdrawal or other independent restriction has made recovery ineligible. A missing, ambiguous or stale item fails closed with the existing block in place.

Only then, in **one domain transaction**, mark A `ABORTED`/closed with its invalidation and `AUTH_DONE` completion evidence permanently retained, without a successful-reset audit or success acknowledgment for A; reserve B as a new operation with one new security-revision increment and its own captured current authority; and transfer `reset_block_operation_id` directly **A → B** with no null or unblocked interval. This step neither repeats A's credential change nor performs B's credential change; B still needs its separate fenced supported auth transaction and ordinary completion-only finalization. A's stale handlers/finalizers cannot revive it, report success or clear B's block. Revocation racing replacement serializes at the same authority/operation barrier: if it wins first, replacement denies; if later, it invalidates B and prevents stale success. No unrelated restriction, staff grant, clinic state or session is cleared.

Reconciliation is therefore a guarded action within the existing recovery-complete flow, not a new public administration endpoint or scheduler. It never guesses from a timeout alone. To abandon a verified expired/incomplete attempt, preserve its proof binding and security evidence without success audit or unblocking. Only the separately proved revocation-invalidated `AUTH_DONE` branch above may close such a completed attempt `ABORTED`; its original auth effect and completion remain historical evidence and are never reported as coordinated reset success. A stale auth handler/finalizer cannot act on a closed operation. Passwordless reconciliation cannot perform an uncommitted credential change; that requires a new valid proof and credential submission. Missing completion is never reset success. If supported adapter mapping/atomicity cannot be proven, the affected task remains ERROR/BLOCKED; do not ship a weaker flow.

Login/session creation must honor the captured-revision rule across reservation, auth, finalization and reconciliation. Merely deleting preexisting sessions misses an in-flight old-password login. Verification hash storage and exact boundary checks must be inspected in persisted rows, not inferred from option names; the installed native expiry comparison alone may accept equality.

The block/reconciliation mechanism is security metadata under D-02/B-04, not a new account-management feature. It does not permit Owner disable/removal that violates the ACTIVE Owner database invariant: separate authorization block from the Owner's persisted enabled/verified association.

## 6. Shared post-commit nonclinical sender

### Claim, abandonment and fencing (U2)

One narrow entrypoint consumes a committed job ID or claims eligible metadata jobs. Use the D-09 job row, not a second lease table. States are `READY`, `CLAIMED`, `SENT`, `CANCELLED` (proof no longer usable) and `FAILED` (nonretryable/exhausted under configured policy). `READY` may have a future `not_before`. Each claim records a fresh `claim_owner`, strictly increasing `claim_generation`, `claimed_at`, `lease_expires_at` and incremented attempt count. A process ID alone is not an owner token.

1. In a short metadata transaction, select eligible rows with `FOR UPDATE SKIP LOCKED`: due `READY` jobs or `CLAIMED` jobs with `lease_expires_at <= db_now`. Sample database wall-clock time after locking; do not use a caller's clock or an old transaction-start time. Recheck current eligibility, proof usability and configured attempt policy on the locked row. Cancel expired/revoked/superseded/consumed proof jobs without sending; otherwise replace the owner, increment generation and persist a new lease atomically. Two reclaimers cannot acquire the same generation. Commit before decrypting or calling SMTP.
2. Before handing material to SMTP, verify that this owner/generation still has an unexpired lease and the referenced proof is still usable. Use a bounded whole-attempt deadline shorter than the configured lease, including subprocess/transport time; no arbitrary production duration is selected here. No heartbeat or background lease-renewal loop is needed. A process that observes expiry or loses ownership stops further send work and cannot renew/resurrect its old generation. Proof revocation after this check may still race delivery, but the resulting link cannot bypass authoritative consumption checks.
3. Finish success, retryable failure or terminal failure in a short transaction conditional on `state=CLAIMED`, matching job/owner/generation and `lease_expires_at > db_now` sampled after the row lock. Exactly one affected row is required. Success sets `SENT`; retryable failure sets `READY` with configured `not_before`; nonretryable/exhausted work sets `FAILED`. Terminal transitions clear claim fields and dispose of delivery ciphertext when no longer needed, without changing issuance audit. A zero-row result means lost ownership: discard the outcome, make no retry/terminal/material update and do not send again in that invocation. A stale owner cannot mark a replacement's attempt sent, reschedule it or delete its material, even if it reports SMTP success.
4. Crash before claim commit leaves no claim. Crash after claim commit (before send or after SMTP acceptance) leaves `CLAIMED` until lease expiry. The next **explicit one-shot invocation** can reclaim it through step 1; no timer, sweeper or periodic scheduler is introduced in Wave 1. If nobody invokes the path, recovery waits. Missing key/transport/configuration fails closed; never fall back to inline or plaintext delivery.

The configured attempt deadline, lease and retry bounds are required operational inputs, with labeled synthetic fixtures for boundary tests and no production defaults selected. B-25 later schedules this exact claim/reclaim/send path; it does not introduce another recovery algorithm. Claim fencing controls database ownership, not an SMTP server: a paused old sender or an acknowledgment lost after remote acceptance can still cause duplicate messages across generations. Retries retain the same job and proof and cannot duplicate logical account/reset effects. Do not claim exactly-once SMTP.

### Token encryption and end-to-end execution (U3)

Use direct **RSA-3072 OAEP with SHA-256 for both OAEP and MGF1** on the exact UTF-8 proof token, not a URL, email body or generic JSON payload. Persist only `{version:1, key_id, ciphertext_base64url}` in restricted delivery-material storage; verifier rows remain digest-only. The OAEP label is the compact, fixed-order UTF-8 JSON array of strings: protocol tag `carepulse-delivery-v1`, key ID, job ID, proof reference, purpose, tenant ID, committed intended recipient and expiry as UTC epoch-milliseconds. No optional whitespace, duplicate fields or alternate encoding; use cross-language vectors, including Unicode, to prove identical label bytes. Sender reconstructs the label from committed issuance metadata, not caller-chosen replacement metadata. Changing job/proof/purpose/recipient/expiry/key context or tampering with ciphertext must fail decryption or proof binding. Recompute and compare the decrypted token's verifier digest before sending. OAEP is not AEAD or issuer authentication: restricted job writes and the committed proof association establish authority; link acceptance still verifies the original digest/state.

RSA-3072/SHA-256 accepts at most 318 plaintext bytes; ciphertext is exactly 384 bytes before base64url. Invitation proof uses 32 random bytes encoded base64url; native recovery proof must also fit. Reject oversize/invalid tokens, invalid encodings, unexpected version/key/length and wrong context without truncation, algorithm negotiation or hybrid/plaintext fallback. Use reviewed PyCA `cryptography` for Python encryption and native Node crypto for recovery encryption/decryption, explicitly specifying SHA-256 rather than Node's SHA-1 default. No application-managed AES content key, wrapping, nonce or tag is needed for this bounded token. The alternatives and complete operational cost are recorded in [research §7](../research.md#7-committed-mail-and-delivery-secrets).

The dedicated delivery key pair is independent of auth, service-signing and clinical-file keys. Issuers receive only public material. Private keys are mounted only into the trusted sender invocation/container, including its Python launcher; Docker secret mounts do not isolate a Node child from its same-UID Python parent. Metadata listings, staff and operator commands cannot retrieve ciphertext or private material. Publish the new public key before switching issuance; retain older private keys while their jobs remain deliverable. Dispose of ciphertext on sent/terminal-unusable work without changing immutable audit. Production custody/rotation/backup approval remains OPEN; no production retention duration is invented.

Execution boundaries:

- **Python issuance**: allocate job/proof IDs, generate token/digest and OAEP-encrypt before business locks. Then recheck current authority/expected revisions and atomically write proof, material, job and audit. Encryption failure leaves no issuance/reissue/revocation effects. No Node subprocess is needed in API/operator issuance.
- **Better Auth recovery issuance**: the existing supported atomic issuance integration encrypts with native Node crypto and commits digest verification/material/job/evidence in the same adapter transaction. The in-process encryption call does not send mail or call Python. Where token creation is inside that transaction, use already-loaded public material; no external key lookup or process work inside it.
- **Post-commit delivery**: Python owns claim/reclaim and finish state. After claim commit, invoke one fixed Node mail adapter with bounded stdin containing ciphertext and committed delivery context; no token, secret or link in argv/environment/stdout. Node decrypts in memory, validates binding, constructs an allowlisted same-origin link, and calls the existing Nodemailer transport. Return a bounded sanitized outcome only; Python finishes with the lease/generation predicate above. Never return the raw token to the launcher. Use synthetic recipients only in Mailpit; keep message bodies/traces out of logs/artifacts.
- **Packaging**: add one reviewed exact Python crypto pin and hash-locked binary-wheel closure during authorized implementation; preserve existing pins. Keep API/operator images Python-only. Include the already-pinned Node runtime and only shared mail modules/locked transport closure in the existing worker/sender target, not the entire Next server. Extract mail-only config validation so sender execution requires no BFF auth/service secret. Give its one-shot invocation narrowly scoped nonclinical DB credentials, private-key mounts and private SMTP network reachability (absent from today's DB-only worker network). Issuer/operator/web executions never receive the private mount. CLI/CI orchestration invokes this existing worker target separately after commit; do not mount a Docker socket, add a listener/service or move domain rules into Node. B-25 later schedules this exact Python-owned path.

This replaces the earlier hybrid-envelope/Node-issuance-codec design choice, not an approved architecture or medical-file encryption requirement. The completed U1/I1/U2/U3 reconciliation aligns `tasks.md` with the direct RSA-OAEP token and issuer/sender packaging contract. Reconciled tasks do not authorize implementation.

Do not modify immutable issuance evidence, mint replacement proof or change recipient/purpose during a delivery retry. Required missing key/transport/storage fails closed without inline fallback.

B-03 first-Owner and B-04 recovery tests invoke the **same** sender after issuance commit and verify rollback leaves no deliverable job. B-25 later supplies periodic scheduling/retry of this path. Wave 1 adds no scheduler, worker service behavior, clinical outbox delivery or new mail daemon.

## Required protocol proof

Real DB and auth evidence must cover golden signing vectors and tampering; concurrent nonce replay after both successful/failed domain work; no-context/cross-tenant and pooled cleanup; duplicate idempotent creates with fresh nonces; old-session/old-password-login races; exact expiry/throttle boundaries; Owner activation/reissue/suspension; atomic proof+job issuance; every reset competitor/failure outcome in §5; abandoned claims and expired/stale-owner fencing in §6; Python↔Node OAEP interoperability, tamper/wrong-context/oversize rejection, missing keys, key overlap and sender secret/network isolation. These tests prove only available Wave 1 commands/substrate, not later SSE, booking, Visit or queue behavior.
