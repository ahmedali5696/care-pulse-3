# Full Foundation scalability review

**Decision requested.** Authorize a profiling experiment at a frozen revision after independent review. The first partition worth testing uses two current-head runners. Ten existing Ordinary invocations move as a unit to a database-only runner. The existing full-stack runner retains all service-dependent scenarios. The baseline model gives **11m50s** elapsed versus **19m52s** observed, at approximately **28.0 versus 26.6 aggregate runner-minutes**. Runner availability, fresh-database behavior and equivalent evidence are the conditions on that estimate.

## Cost model and alternatives

The ten proposed moved invocations total 488.76s of pytest time or **494.03s** measured from their respective Compose test-container creation to pytest summary. Conservatively leave their trailing shell time on stack. Stack projects to **567.97s** (1,062 − 494.03). A same-SHA admission diagnostic provides a DB-only comparison: its job took 161s, with 75.55s from test-container creation to focused result, leaving **85.45s** for runner/bootstrap/build/DB/cleanup. Its test image build took 18.24s. Different Ubuntu image build and diagnostic runner, and no Full receipt upload, make 85.45s an estimate for the new shard's fixed cost. [Diagnostic job and log](https://github.com/ahmedali5696/care-pulse-3/actions/runs/45621724678)

| Scenario | Wall time calculation | Elapsed | Aggregate runner-min |
|---|---|---:|---:|
| Observed baseline | 130s outside Ordinary + 1,062s | 19:52 | 26.62 |
| Two current-head jobs, runners immediately available | 130 + max(567.97, 494.03 + 85.45, 162, 256) | ~11:50 | ~28.04 (+1.42) |
| New DB job costs an additional 45s | Same model, DB job 624.48s | ~12:34 | ~28.79 (+2.17) |
| New DB job queues for two minutes | Its critical finish moves to 699.48s after fan-out | ~13:49 | ~28.04 if only queue time changes |

The nominal saving is **8m03s (40%)**. Wall time and total runner-minutes measure different costs. Per-job whole-minute rounding, if applied, gives 29 baseline minutes and roughly 31 nominal proposed minutes. Account billing and available concurrent slots were not measured. The comparison assumes equivalent fixture/data behavior, the same common and gate time, and four simultaneous integration slots. A slower cold image build or lost queue priority can outweigh the roughly twelve-second modeled difference between the current-head jobs.

* A Wave-3-only split would move 361.60s of pytest work and leave a larger tail on stack. The proposed group adds F-01 and D-08 using measured durations and preserves F-01 → D-08 order. Moving B-09 in place of F-01 would give a similarly balanced time but break the explicit B-09 → D-11 sequence. Keep files and race pairs intact. Avoid assignment by case count, random shuffling or historical duration from another schema.
* With constrained concurrency, retain today's topology and first profile the heavy cases. Reordering tiles on one serial runner alone saves no compute. Fusing the ten container launches can recover only part of the observed ~5.27s between their creation-to-summary times and pytest times, plus post-summary shell overhead. A merged pytest process would also alter module-fixture lifetimes and per-report evidence.
* Install Playwright and build the full service images only on stack. DB-only still builds the real test target, including its locked Node stage, and uses the same effective per-invocation secret mounts. The template or seed database idea would change fresh-install, grant, rollback and historical evidence. Consider reuse only for demonstrated immutable setup, with a fresh mutable identity/tenant per case and measured fixture savings. Cross-run DB volumes, pre-seeded credentials and cached test outcomes are outside this design.
* A third current-head group would require another private environment, more slots, receipts and setup time. Revisit only when measured shard imbalance persists or one coherent group becomes the critical path. Weight reviewed whole-suite assignments from recent comparable runs and keep assignments fixed for an executing SHA/attempt.

Earlier work already introduced pinned toolchain/download caching and independent historical and compatibility jobs. Run 45195062101 took 18m29s on the older design, and the 10m00s profiling experiment at d4be166 was explicitly profiling-only. PR 31 subsequently established permanent three-lane receipts and special-mode protections. Those runs used different code and coverage. Their times are unsuitable as an A/B estimate for splitting today's Ordinary lane. ## Profiling candidate and review gates

The companion [opt-in pytest profiler](../ops/profile_ordinary.py) runs one existing invocation. It records each case's file, function, position in execution order and setup/call/teardown wall time. It separately times named fixture setups and generator fixture bodies resumed during teardown. Explicit callbacks outside generators are included in the case's teardown total. Wider-scoped finalizers are charged to the case where pytest runs them. Named fixture times are breakdowns within phase totals and can include nested work. Raw parameters, node IDs, exception text, SQL, environment and credentials are absent from the timing JSON. The wrapper preserves pytest failures and returns nonzero for missing, skipped, incomplete or xfail-marked cases. Each output is created exclusively.

For a separately authorized experiment, use a profile-only job identity and private synthetic environment with the baseline controller's setup, selection, mounts and cleanup. Give the controller the reviewed profiler as a read-only file or include it in the test image. In the existing Compose invocation replace only the inner `python -m pytest` with `python -m ops.profile_ordinary PRIVATE_JSON`, forwarding the original flags, all module names, deselections and JUnit output. For example, the inner Queue Scope command inside the existing test service is:

```sh
python -m ops.profile_ordinary /tmp/foundation-results/profile-queue-scope.json \
  -q -s -ra --tb=short -p no:cacheprovider \
  --junitxml=/tmp/foundation-results/w3_queue_scope.xml \
  tests/integration/test_w3_queue_scope.py
```

Keep private stdout/stderr and timings inside scoped cleanup. Retain only reviewed sanitized aggregates with measured SHA, profile code identity, run/attempt, suite and runner image. Use profile-only names throughout and disable Full receipt sealing, upload and the acceptance marker in the experimental controller. No workflow calls this tool at baseline. Its local synthetic smoke checks cover passing parameter cases, named fixture setup and generator teardown, failure, skip, and missing selection. These checks establish the measuring tool's behavior only.

1. **Profile after PO approval.** Measure the seven focus invocations in their original serial order and DB history, including the ordinary intervening suites. Record outer monotonic intervals for pulls/build, TCP readiness, role bootstrap, head upgrade, identity seed, each invocation, service startup and cleanup. Keep an uninstrumented control. If call time dominates, time only the named helpers implicated by the measured case (e.g. F-01 upgrade/snapshot or queue data construction) in a second profile. A fixture optimization requires evidence that setup is material and that its state can be isolated.
2. **Prove partition parity before changing acceptance.** At a frozen application/migration/test tree, run comparison-only old-order and split controllers, on fresh databases, retaining exact test and orchestration identities privately. Compare per-report selected node multisets and outcomes, TAP counts and ordered scenario markers, historic deselections and shell gates. Require exact union, zero unexplained overlap/omission, zero mandatory skips and clean teardown for every participant. Check the suggested 446/605 mapping against the actual target SHA. Reconcile new Wave 3 work before moving the baseline forward.
3. **Measure cost before promotion.** Proposed decision threshold for PO review: at least three complete matched comparisons, same runner class and pinned inputs; report each run's SHA, attempt, queue, wall time, summed runner time and any cold builds. Target median elapsed improvement ≥30% and added unrounded aggregate runner time ≤3 minutes per Full run. Report exceptions, cancellations and variance. Keep each result intact; performance comparisons confer no Full acceptance.
4. **Permanent work needs separate authorization.** Change only orchestration, manifest/report validators, receipt contract, coverage tests, documentation and the reviewed workflow fingerprint. Exercise fail-closed cases for missing/duplicate/foreign/stale evidence, failed/skipped/cancelled jobs, missing nodes, unexpected artifacts, wrong head and cleanup failure. Verify Full successes include all four current-attempt receipts and exact SHA. Exercise the non-Full matrix and existing special-mode rejection guards without authorizing a positive T133 run on this branch. Require a successful complete Full workflow at the final executable SHA, all jobs in one attempt, before integration acceptance.
