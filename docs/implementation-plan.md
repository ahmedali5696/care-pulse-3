## 1. Purpose, scope and authoritative sources

Implement the simplest secure, correct CarePulse clinic MVP defined by these immutable authorities, in descending precedence:

1. `CarePulse_PRD_v1_APPROVED.md` (19 October 2026): product scope, FR/BR/AC and role matrix.
2. `CarePulse_Domain_Model_State_Machines_v1_2_APPROVED.md` (19 October 2026): INV-01–38, CON-01–45, six-state machine and command boundaries, subordinated to the PRD.
3. `CarePulse — System Design v1.0.md`: approved Modular Monolith, stack and security topology, subordinated to both above.

**Included:** multi-tenant, single-Doctor/Owner, single-branch, non-billed clinic operations; Receptionist access; restricted internal tenant provisioning; patient directory/family lookup; Open/Exact-Time booking; main Routine/Paid Urgent and independent Emergency FIFO lanes; admission/Visit; follow-up; configuration; date-specific reconciliation; eligible same-day cohort bulk **rescheduling**; internal realtime and consented Doctor push; scanned medical attachments; single-patient PDF/CSV export; reports, audit and recovery preparation; Arabic/English interface.

**Not included:** patient login or payments, SaaS checkout/subscriptions/trials/public registration/admin dashboard, bulk cancellation, structured E-Prescriptions, patient WhatsApp/SMS, record merge/deletion, multi-Doctor/branch/currency/timezone, patient portal, speculative integrations. **Paid Urgent is a premium service, not a recorded payment.**

**Authority and consistency finding:** no material direct conflict was identified in the operative PRD/Domain/System Design rules that prevents creation of an implementation plan. Some documents anticipate standalone Security Specification, Acceptance Matrix or API Contracts; the Product Owner's present instruction consolidates their necessary implementation-level content **in this plan**, without modifying the approved product rules. Domain §9.5 labels metric formulas technical design proposals: this plan adopts them as documented implementation decisions, not amendments to the PRD. Open numeric/legal decisions remain unresolved gates in §14, not implementation defaults.

**Reference convention:** `FR-*`, `BR-*`, `AC-*` from PRD; `INV-*` and `CON-*` from Domain. An inclusive range names existing identifiers only; missing numeric IDs are never silently created. All acceptance criteria `AC-01–43` are active. No prior CarePulse versions govern this plan.

**Date/policy precedence:** A valid explicit date override controls the operating intervals for that date; otherwise use configured weekly periods, but a holiday marked closed cannot invent timed operating hours: an ordinary holiday Exact-Time booking needs a positive, explicitly applicable date-specific opening period as well as the holiday-booking toggle. A newly created QueueDay snapshots the latest queue policy effective for its clinic-local operating date; edits made during an existing date never replace that date's snapshot. If no working **hours** exist, create dated QueueDay on first authorized attendance (including valid Open day-only attendance) without inferring an end time; next-operating-day effectiveness is determined from the configured working-day calendar and actual approved service-day eligibility, never a midnight queue migration.

**Reasoned security choice:** The single internal BFF-to-API signing key plus one PostgreSQL nonce row per accepted request is retained because explicit replay and forgery resistance is required even if another container reaches the private network. Use the existing DB rather than introducing mTLS infrastructure, a gateway, Redis or a token broker; review per-request DB overhead against production workload, without removing replay tests.

**Technical requirements for the identity envelope:** Canonicalize with stable UTF-8, query ordering and raw body-byte hashing. Verify against the exact received route/body; reject missing/duplicate identity headers, invalid key ID, stale/reused nonce, forged signature and non-BFF sources. Store nonce unique by `(key_id, nonce)` in a protected database table until its authenticated timestamp falls outside the configured maximum accepted freshness/skew window; purge only after it is **provably no longer acceptable**. A deployment-configured accepted freshness/skew policy is required and is **not** assigned a product/security number here. Use constant-time digest comparison. Strip/overwrite any inbound `X-CarePulse-*` identity headers at BFF. Sign only after Better Auth server session validation. Do **not** forward bearer session cookies to FastAPI. Same-origin cookie + CSRF/origin checks protect BFF mutations. Runtime can reject requests when required security policy is unset; test environments inject explicitly labeled test-only values.

**Operator authentication and invitation activation:** A restricted, audited **one-shot internal CLI** runs only inside the operator Compose profile, with no network-listening operator API, no host-exposed endpoint and no public signup. The CLI connects using a separate **metadata-only** DB role; runtime and operator grants cannot SELECT/UPDATE clinical records. Each action requires an individually issued high-entropy operator credential (digest matched to an enabled `operator_identities` record), validated operator identity and explicit reason; constant-time comparison, rate limiting, least-privilege table/function grants and durable operator audit apply. Never bundle operator credentials into the web/API/worker images or pass them via public HTTP. Public signup is disabled. First-owner verified-email acceptance is handled by the Better Auth server entrypoint and serialized using Organization/invitation row locks: auth identity may be prepared before the final tenant transaction, but remains **non-active/unusable** until that transaction verifies identity, single-use token, uniqueness and then atomically establishes the staff Owner association and sets the tenant ACTIVE. A failed/interrupted preparation must remain PROVISIONING and may be safely retried/reconciled without activating a second Owner. **Bootstrap exception:** the verified invite-acceptance BFF route may call only an explicitly allowlisted FastAPI owner-activation command for a PROVISIONING tenant, using the signed BFF identity/service channel plus one-use invitation proof and Organization row lock; this is **not** an authenticated ACTIVE-tenant clinic session and grants no patient/clinical/settings operations before activation. Reject all other protected clinic commands while tenant is PROVISIONING. Do not assume a cross-process Better Auth API call participates in a Python transaction.

**Recovery and revocation ordering:** Disable/grant removal/tenant suspension first commits a live authorization-state/security-revision change; any still-valid Better Auth session is already denied by FastAPI and the BFF live-session endpoint, then all associated sessions are invalidated. For owner password reset, the Better Auth recovery handler must consume the verified token, change credential and invalidate existing auth sessions in one durable auth-database operation as supported/tested by the chosen adapter; if it cannot guarantee this, keep that identity blocked in application authorization until reconciliation, rather than report reset success with valid old sessions. The implementing agent must verify actual adapter behavior against tests, not assume a particular Better Auth API method name/version.

**Field permissions:** The binding field-level mapping below implements PRD §3/FR-003/069/080 and Domain §12.1 without creating new product data classes. Permission applies identically to response DTOs, search, SSE, attachment listings, downloads and mutation DTOs; omitted field access is **DENY**. `Doctor` denotes the single Doctor/Owner of that tenant; `Receptionist` denotes enabled staff with live tenant authorization. An operator has no clinical row access. An allowed *write* never grants an implicit *read* of another classification or cross-tenant data.

## 3. Agent execution rules and testing strategy

1. Execute an unblocked task by its task ID and explicit `Depends`, not by waiting for a whole Wave. Read the relevant cited portions of the three authorities **and this plan**; never follow older documents over them. Do not implement without explicit plan approval.
2. For every functional task: **implement production code → add focused tests → run them → fix confirmed defects → check acceptance evidence → mark done.** Never require red-first TDD.
3. Each task completion report must include: task ID, files changed, migrations if any, refs validated, concrete positive/negative/race checks, commands and results, and unresolved limitations. `IMPLEMENTED` means code exists; `TESTED` means required checks pass; `LOCAL VERIFIED` means tested through runnable Compose integration; `PRODUCTION READY` requires all §14 gates and deployment evidence. Do not conflate these.
4. Preserve atomicity and exact six Appointment statuses (`Booked`, `Waiting`, `In Examination`, `Completed`, `Cancelled`, `No-show`). Derived `requires_review`, QueueEntry states, scanner states and DayReview are **not** additional Appointment statuses. Forbidden transitions must return a denial with **zero successful domain writes and zero outbox events**.
5. Tests use repeatable isolated tenant fixtures, deterministic Cairo/UTC clock injection, and actual concurrent database connections for races. Check rejected requests leave no orphan number, queue entry, Visit, claim, status, price, successful audit or outbox. Test every important allowed path and denial; no exhaustive permutation explosion.
6. **Anti-loop:** after two unsuccessful correction attempts for the same failure, capture failing command/reproduction, expected vs actual behavior, suspected cause and proposed single fix; stop attempting random rewrites. Never remove a valid security/business assertion merely to turn green.
7. Schema changes are incremental, reversible when safe, migration-reviewed, and never automatically applied to production. Source authorities and release-gate records are not altered by coding agents.

## 11. Shared backend/API, security and reporting contracts

These contracts apply across **all Waves**; reference the shared rules rather than redefining them differently in separate implementations. FastAPI owns product rules; Next.js App Router BFF owns Better Auth session verification, CSRF/origin enforcement, request signing and reverse proxy only. ### 11.1 Backend wire/API contracts — binding for implementing agents

**Transport:** browser calls only Next `/api/*` with secure same-origin session cookie; BFF validates Better Auth and signs private `/v1/*` to FastAPI. The CLI in B-03 is **not** a FastAPI route. JSON with snake_case wire field names; RFC3339 UTC for event instants, `YYYY-MM-DD` for service day, monetary amounts as EGP decimal strings. Stable machine enums independent of language. `organization_id`, actor, role, price, rank, Visit identity, status and audit actor must be derived server-side; client input for such authority is rejected/ignored safely, never used as access grant. `GET` is read-only; mutations require SameSite secure cookies + Origin/CSRF enforcement at BFF, explicit request schema; no state change on `GET`. Pagination for patient/timeline/audit/report lists; tenant-capped server pages, without inventing clinical limits. No `/bulk-cancel`, `/billing`, `/e-prescription`, public registration or patient message endpoint.

**Common success:** `200/201 {data, revision, event_id?}`; preview returns `{preview_id, eligible[], excluded:[{id,reason}], affected[], revisions}` as appropriate. **Common failure:** `401` invalid session, `403` live role/tenant denial, `404` non-visible resource (avoid tenant existence oracle), `409` state/day/lock/revision conflict with symbolic `code`, `422` invalid values/transition/schedule, `429` recovery/login throttle, `503` required scanner/mail/storage/security dependency unavailable (never silently bypass). Error shape `{error:{code,message,request_id}}`, with no PHI or sensitive server details. `Idempotency-Key` on create, intake, admit, cancel/replacement, reschedule, bulk, finalize and export creation: identical normalized actor+operation+body returns committed result; same key/different body → `409 IDEMPOTENCY_CONFLICT`. Revision and preview expiry/invalidation are checked inside commit; a `409` is an instruction to re-fetch/preview, never automatic bypass. Denials have no committed business/outbox side effect (security denial evidence may be separately logged without PHI).

- **Admission:** lock shared Doctor control **before** chosen date/lane, recompute eligible head without cross-lane preemption, recheck Doctor Pause, live actor/mode, active In Examination across **all dates**, consume one case-specific Doctor confirmation if extra capacity, capture prior-day reconfirmation in same transaction, create unique Visit + close queue + status/audit/outbox; only an **ordinary MAIN Routine head** moves the missed-turn cursor. Stale or forged lane/head/revision is `409`/`403`, not a fallback selection.
- **Follow-up/cancellation:** lock original Completed source and claim ledger; issue one active claim at a time; Completed marks durable consumed exactly once. Cancellation/No-show releases active claim in the **same** transaction, including Doctor exceptional In Examination cancellation with retained Visit. Confirmed deadline/price survives future policy change; deadline extension is Doctor-reasoned/audited before moving outside it.
- **Schedule/bulk:** preview binds actor, tenant, original day, selected IDs, relevant revisions and conflict set. Commit locks in stable order, calculates fresh eligibility and interval conflicts and either applies every selected eligible Routine cross-day reschedule or **rolls back all**, with old Waiting entry closed and Booked refreshed. Orphan temp objects are safe to garbage-collect; rollback cannot expose them. Download permissions are checked **when the content is served**, not only at URL issuance; support one-use bounded grants with revocation. Export is one-patient Owner-only and audited.
